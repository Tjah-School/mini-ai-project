## **1\. Software**

### **1.1 What is Software? System Software vs. Application Software**

**Learning objectives**

* Define software and explain why hardware needs it.  
* Distinguish system software from application software with examples.  
* Classify an unfamiliar program using the *who does it serve?* test.

**Core concepts**

* **Software** is a set of intangible digital instructions, rules and data that tell physical hardware what to do *(PDF: Foundation of Software)*. It is stored on hardware but is not the hardware.  
* **System software** is the foundation between hardware and applications. It manages core resources (memory, processor time, storage access) and provides a user interface. Examples: Windows 11, macOS, Linux, Android, iOS and device drivers such as an NVIDIA GPU driver.  
* **Application software** performs specific tasks for the end user: web browsers (Chrome, Firefox), office tools (Word, Google Docs), media players (Spotify), games (Minecraft). It relies on system software to run.  
* **Classification test (extra):** ask who the program mainly serves. If it serves the *machine and other programs*, it is system software; if it serves a *person's task*, it is application software.  
* **Boundary case:** a video site such as YouTube is used by people to watch videos, so it is application software, even though it runs through a browser.

**Real-world analogy (PDF): music and performance.** Hardware \= the instruments. Software \= the sheet music and arrangement. Executing code \= the musicians playing. System software \= the conductor coordinating all instruments; application software \= the specific song being performed.

**Worked example.** Classify: YouTube, Windows, macOS, NVIDIA GPU driver, Minecraft. Answer: YouTube \= application; Windows \= system; macOS \= system; NVIDIA driver \= system (it lets the OS control the graphics card); Minecraft \= application.

### **1.2 Operating Systems: Evolution, Process Management and Memory Management**

**Learning objectives**

* Describe how operating systems evolved.  
* Explain what a process is and how the OS schedules processes.  
* Explain memory allocation, protection and virtual memory.

**Core concepts**

* **Evolution (slides \+ extra):** batch systems (jobs run in groups, no interaction) → multiprogramming and time-sharing (several users share the CPU by fast switching) → personal computers and graphical interfaces → mobile and distributed systems. **UNIX** is a classic multi-user, multitasking OS *(slides: sample material)*.  
* **Process management:** a *process* is a program in execution. States: new, ready, running, waiting (blocked), terminated *(extra)*. The **scheduler** picks which ready process gets the CPU; a **context switch** saves one process's state and loads another's.

<div align="center">
<img width="50%" height="50%" alt="image" src="https://github.com/user-attachments/assets/5fc4e0ac-bf87-4359-99b6-05e6b62a26d4" />
</div>

* **Scheduling policies (extra):** first-come-first-served, priority, and **round robin**, where each process runs for a fixed time slice (quantum) and then goes to the back of the queue.  
* **Memory management:** the OS allocates main memory to processes and **protects** each process from reading or writing another's memory. **Virtual memory** (paging) lets a program use more address space than physical RAM by keeping inactive pages on disk. A **page fault** happens when a needed page is not currently in RAM.

**Real-world analogy: a restaurant kitchen.** Orders are processes, the chef is the CPU, the counter space is RAM, and the head chef (the OS) decides whose order is cooked next and makes sure two orders do not share one cutting board.

**Worked example (round robin).** Quantum \= 2 ms. P1 needs 5 ms, P2 needs 3 ms, P3 needs 2 ms. Run order: P1(2), P2(2), P3(2, finishes), P1(2), P2(1, finishes), P1(1, finishes). P3 finishes first, then P2, then P1.

### **1.3 How Code Runs and How it is Translated: Compiled vs. Interpreted**

**Learning objectives**

* Explain why high-level code must be translated.  
* Compare compilers and interpreters, with trade-offs.  
* Trace print("Hello") from source text to hardware execution.

**Core concepts**

* **High-level code** (Python, C++, Java) is readable by humans. **Machine code** is binary (0s and 1s) matching electrical signals: ON \= 1, OFF \= 0, processed by transistors in the CPU *(PDF)*.  
* The CPU cannot read text like print("Hello"), so a **translation layer** parses the code, checks syntax and produces machine instructions.  
* **Compiler** *(PDF: C++, Rust)*: translates the entire source file before execution. Fast runtime, but an extra build step.  
* **Interpreter** *(PDF: Python, JavaScript)*: reads and translates line by line while running. Easy to test and edit, slightly slower.  
* **Typical compiler stages (extra, Aho et al.):** lexical analysis (tokens) → parsing (syntax tree) → semantic checks → code generation.  
* **Hybrids (extra):** Java compiles to *bytecode* that a virtual machine runs; Python also compiles to bytecode before interpreting it; many JavaScript engines compile hot code at run time (JIT).

**Real-world analogy (PDF): the robot chef.** The robot understands only piston UP/DOWN and heater ON/OFF. The compiler is a translator who converts the whole English recipe ("Bake at 350°F") into switch commands before cooking; an interpreter translates one sentence at a time while the robot cooks.

**Worked example.** The text Hello in ASCII: H \= 72 \= 01001000, e \= 101 \= 01100101. A real run: source → translator → binary instructions \+ data → CPU executes them → the screen driver shows the text.

### **1.4 Programming Languages and Program Logic**

**Learning objectives**

* Trace the evolution and paradigms of programming languages.  
* Use sequence, if/else and loops to express logic.  
* Explain integer limits and overflow with a concrete case.

**Core concepts**

* **Generations (slides \+ extra):** machine language → assembly (mnemonics, translated by an assembler) → high-level languages (FORTRAN, C) → 4GL such as SQL → modern multi-paradigm languages.  
* **Paradigms:** imperative/procedural (C), object-oriented (Java, Python: encapsulation, inheritance, polymorphism), functional (Haskell), logic/declarative (Prolog, SQL).  
* **Language features:** syntax (form), semantics (meaning), data types, variables, control structures, abstraction.  
* **Program logic (PDF: How Do Programs Think?):** software turns inputs into outputs by combining simple blocks. **If/else** chooses a path from a True/False condition. **Loops** repeat a block until a condition changes or for every item.

<div align="center">
<img width="50%" height="50%" alt="image" src="https://github.com/user-attachments/assets/be87060b-e0b5-4df1-ba23-bab1201ba700" />
</div>

* **Structured program theorem (Bohm & Jacopini, 1966):** sequence, selection and iteration are enough to express any computable function *(listed in the PDF's sources)*.  
* **Integer limits (PDF):** a 32-bit signed integer stores at most 2,147,483,647 (2^31 − 1). Going past it overflows.

**Real-world analogy: a smart thermostat (PDF).** Input \= temperature sensor. If/else: IF room\_temp \> target THEN cool ELSE stop cooling. Loop: WHILE cooling is active, check the temperature every minute. Output \= cool air.

**Worked example (game cheat).** Setting money to 999,999,999 fits in 32 bits, but adding 2 billion more would pass 2,147,483,647 and may wrap to a negative number or crash. A safe program checks a limit before adding.

### **1.5 How Software is Built: Software Engineering, the SDLC and version control**

**Learning objectives**

* List the SDLC steps and what each produces.  
* Compare waterfall, spiral and agile process models.  
* Explain modularity, testing levels and why version control exists.

**Core concepts**

* **SDLC (PDF: five core steps):** Plan (requirements and audience goals) → Design (UI and system architecture) → Code (write source to specification) → Test (find bugs, security flaws, performance issues) → Release (deploy and keep updating). Maintenance after release is part of the lifecycle *(extra)*.

<div align="center">
<img width="50%" height="50%" alt="image" src="https://github.com/user-attachments/assets/83733d7e-7f19-4696-a7b4-c59ce64c6c27" />
</div>
  
* **Process models (slides \+ extra):** *waterfall* (phases in sequence), *iterative/incremental*, *spiral* (risk analysis in every loop), *agile* (short iterations, frequent feedback). The **Agile Manifesto** (2001) values individuals and interactions, working software, customer collaboration and responding to change, *over* (not instead of) processes, documentation, contracts and plans.  
* **Modularity (slides):** split the system into modules with **high cohesion** (one clear job) and **low coupling** (few dependencies); *information hiding* exposes only an interface.  
* **Quality assurance (slides \+ extra):** unit tests (one function), integration tests (modules together), system tests (whole product), acceptance tests (does it meet the customer's needs); black-box versus white-box testing; code review.  
* **Version control (PDF: Git/GitHub):** records changes to files over time so earlier versions can be recalled. Git is a *distributed* system created by Linus Torvalds for Linux kernel development; **GitHub** hosts Git repositories online. A *branch* lets work proceed in isolation, then it is *merged*.

**Real-world analogy: building a house.** Plan \= client brief; Design \= blueprint; Code \= construction; Test \= inspections; Release \= handing over keys. Version control is the dated set of blueprint revisions, with a separate copy for experiments.

**Worked example (login feature).** Plan: users must sign in with a password. Design: login screen \+ credential check module. Code: implement it. Test: unit-test the password check, integration-test with the database, acceptance-test with a user. Release: deploy, then patch bugs. Each change is a Git commit on a feature branch merged after review.

### **1.6 Cloud software and Software as a Service (SaaS)**

**Learning objectives**

* Explain how software delivery moved from local media to cloud services.  
* State the NIST essential characteristics and service models.  
* Weigh the benefits and risks of SaaS.

**Core concepts**

* **From disks to the web (PDF):** software used to be installed from CDs or disks. With **SaaS**, code runs on remote cloud servers and users reach it through a browser or light app over the internet.  
* **NIST definition (SP 800-145):** a cloud model has **five essential characteristics** (on-demand self-service, broad network access, resource pooling, rapid elasticity, measured service), **three service models** (SaaS, PaaS, IaaS) and **four deployment models** (private, community, public, hybrid).

### **1.7 Open Source vs. Proprietary Software**

**Learning objectives**

* Define open-source and proprietary software.  
* Explain what the Open Source Definition requires.  
* Compare licences, benefits and risks of each model.

**Core concepts**

* **Open source (PDF):** source code is publicly accessible to review, modify, inspect and enhance. Examples: Linux, Python, VS Code.  
* **Proprietary (closed source) (PDF):** the company owns the source code; users receive compiled binaries under a licence. Examples: Microsoft Windows, Adobe Photoshop.  
* **Open Source Definition (OSD):** published by the Open Source Initiative in 1998, with ten criteria such as free redistribution and no discrimination against uses. Merely viewing the code is **not** enough to count as open source.  
* **Licence families (extra):** *permissive* (e.g. MIT) allows reuse in closed products; *copyleft* (e.g. GPL) requires derivative works to stay open under the same terms.  
* **Terms to keep apart (extra):** *free software* (freedom to run, study, change, share), *open source* (the OSD), *freeware* (free of charge, source not necessarily open).  
* **Trade-offs (extra):** open source offers transparency and community review but support quality varies; proprietary software often has vendor support and accountability but less transparency and possible lock-in.

**Real-world analogy: recipes.** An open-source recipe is published so anyone can cook, improve and share it under the rules attached; a proprietary recipe is a secret: you buy the dish, not the method.

**Worked example.** A start-up needs a database. Option A: an open-source database; staff can read and modify the code and there are no per-seat fees, but they must provide their own expertise. Option B: a proprietary database with paid support and a service contract. The choice depends on budget, skills and the need for support guarantees.

### **1.8 Databases and SQL**

**Learning objectives**

* Separate a database from a DBMS and name database models.  
* Explain relational tables, keys and normalisation.  
* Write and read basic SQL queries.

**Core concepts**

* A **database** is organised data; a **DBMS** is the software that stores, protects and queries it. **Models (slides):** hierarchical (tree), network (graph), relational (tables), plus object-oriented and NoSQL *(extra)*.  
* **Relational model:** tables (relations) of rows (tuples) and columns (attributes). A **primary key** is unique per row; a **foreign key** points to a primary key in another table. The model was proposed by E. F. Codd in 1970 *(extra)*.

* **SQL (slides):** declarative: you describe *what* you want. Core commands: CREATE TABLE, INSERT, SELECT ... FROM ... WHERE, UPDATE, DELETE, JOIN, GROUP BY with aggregates such as COUNT.  
* **Normalisation (extra):** organise tables to reduce redundancy and update anomalies (first, second, third normal forms).  
* **Transactions (extra):** a group of operations that succeeds or fails as a unit (ACID properties), which protects data during concurrent use.

**Real-world analogy: a library catalogue.** Books, members and loans are separate lists linked by ID numbers; looking up "which member has this book" is a JOIN.

**Worked example.** Student(id PK, name, age); Enrol(student\_id FK, course). SELECT name FROM Student WHERE age \> 20; returns students older than 20\. SELECT s.name, e.course FROM Student s JOIN Enrol e ON s.id \= e.student\_id; lists each student with each course. SELECT course, COUNT(\*) FROM Enrol GROUP BY course; counts enrolments per course.

**True / False**

1. In the relational model, data is stored in tables of rows and columns.  
2. A primary key value may be repeated in two different rows of the same table.  
3. SQL is declarative: the user states what data is wanted rather than how to retrieve it.  
4. In the hierarchical model, a child record may have many parents.  
5. The WHERE clause filters which rows a query returns.
