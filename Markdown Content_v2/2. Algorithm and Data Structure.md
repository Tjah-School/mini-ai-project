## **Topic 2: Algorithms and Data Structures**

An **algorithm** is a step-by-step procedure for solving a problem. A **data structure** is a way of organizing data so the algorithm can use it efficiently. The two always go together: Niklaus Wirth's classic book title, *Algorithms + Data Structures = Programs*, states the idea. Choosing the right structure often matters more than choosing a clever algorithm.

### **2.1 Algorithms: Features, Representation and Efficiency**

#### **2.1.1 What an Algorithm Is**

An **algorithm** is a finite, ordered sequence of precise, executable steps that takes some **input** and produces the desired **output**. A recipe is the everyday analogy: the ingredients are the input, the dish is the output, and each step says exactly what to do.

The word comes from the name of the 9th-century Persian mathematician **al-Khwarizmi**, whose books on arithmetic spread step-by-step calculation methods. One of the oldest algorithms still in use is **Euclid's algorithm** for the greatest common divisor, described around 300 BC.

**Three terms that are easy to confuse**

| Term | Meaning | Example |
| ----- | ----- | ----- |
| **Algorithm** | The idea: the method for solving the problem | "To find the largest number, keep the biggest seen so far" |
| **Program** | An algorithm written in a programming language so a computer can run it | A Python function `find_max` |
| **Data structure** | How the data the algorithm works on is organized in memory | The list of numbers stored in an array |

One algorithm can be written as many programs, and one problem can often be solved by several different algorithms with very different speeds.

**Common misconception:** "An algorithm is the same as a program." A program is one particular expression of an algorithm; the algorithm itself is language-independent.

#### **2.1.2 Features (Properties) of an Algorithm**

Knuth lists five properties that a procedure must have to count as an algorithm. Two more are always expected in practice.

| Property | Meaning | Violated by |
| ----- | ----- | ----- |
| **Input** | Zero or more clearly specified inputs | "Sort the list" with no list given |
| **Output** | At least one result related to the input | A procedure that computes but returns nothing |
| **Finiteness** | It ends after a finite number of steps | A loop that never stops, such as `while true: ...` |
| **Definiteness** | Every step is precisely and unambiguously defined | "Add a bit more salt", "stir until it feels done" |
| **Effectiveness** | Each step is basic enough to be carried out exactly | "Find the best possible move" with no method given |
| **Correctness** | It produces the right output for every valid input | A sort that fails on empty lists |
| **Generality** | It solves a whole class of problems, not one instance | A program that only works on the numbers 3, 1, 2 |

**Worked example: Euclid's algorithm checks every property**

Problem: find gcd(a, b), the largest integer that divides both a and b.

```
while b ≠ 0:
    r ← a mod b
    a ← b
    b ← r
return a
```

**Common misconceptions**

| Misconception | Reality |
| ----- | ----- |
| "An algorithm must be fast." | Speed is a quality measure, not part of the definition. A slow procedure is still an algorithm |
| "Every problem has an algorithm." | Some problems are provably unsolvable by any algorithm, such as the halting problem (Turing, 1936) |
| "If it works on my test cases, it is correct." | Testing shows the presence of bugs, not their absence; correctness needs an argument or proof |

#### **2.1.3 Representation of Algorithms**

An algorithm can be written down in several forms. The choice depends on the audience.

| Form | Strength | Weakness | Best for |
| ----- | ----- | ----- | ----- |
| **Natural language** | Easy for anyone to read | Ambiguous, wordy | First draft, explaining to non-programmers |
| **Flowchart** | Control flow is visible at a glance | Gets large and messy for complex algorithms | Teaching, small decision logic |
| **Pseudocode** | Precise but independent of any language | No standard syntax; cannot be run | Design and textbooks |
| **Programming language** | Executable, testable | Language details distract from the idea | Final implementation |

##### **Flowchart symbols**

| Symbol | Shape | Meaning |
| ----- | ----- | ----- |
| Terminator | Oval | Start or end |
| Process | Rectangle | An operation or assignment |
| Input/Output | Parallelogram | Read data or show a result |
| Decision | Diamond | A yes/no test with two exits |
| Flow line | Arrow | Order of execution |

##### **One algorithm in four forms: find the largest number in a list**

**Natural language:** Take the first number as the largest so far. Look at each remaining number in turn. If it is bigger than the largest so far, make it the new largest. When no numbers remain, the largest so far is the answer.

**Flowchart (text description):**

```
(Start)
   ↓
[ max ← first item ;  i ← 2 ]
   ↓
< i ≤ n ? > --No--> [ Output max ] --> (End)
   │Yes
   ↓
< item[i] > max ? > --Yes--> [ max ← item[i] ]
   │No                           │
   ↓ ←──────────────────────────┘
[ i ← i + 1 ]  --> back to the test "i ≤ n ?"
```

**Pseudocode:**

```
FindMax(list, n)
    max ← list[1]
    for i ← 2 to n do
        if list[i] > max then
            max ← list[i]
    return max
```

**Python:**

```python
def find_max(items):
    largest = items[0]
    for value in items[1:]:
        if value > largest:
            largest = value
    return largest
```

##### **Control structures**

Almost every algorithm is built from three constructs. Böhm and Jacopini (1966) showed that these three are enough to express any computation, which is the basis of **structured programming** (and the reason Dijkstra, 1968, argued against unrestricted `goto`).

| Construct | Meaning | Example |
| ----- | ----- | ----- |
| **Sequence** | Steps one after another | Read a, read b, compute the sum |
| **Selection** | Choose a path by a condition | `if score ≥ 50 then pass else fail` |
| **Iteration** | Repeat steps while a condition holds | `for` and `while` loops (see 2.2) |

**Pseudocode conventions used in this document**

| Idea | Notation |
| ----- | ----- |
| Assignment | `x ← 5` |
| Comparison | `=`, `≠`, `<`, `≤`, `>`, `≥` |
| Selection | `if ... then ... else ...` |
| Counted loop | `for i ← 1 to n do` |
| Conditional loop | `while condition do` |
| Result | `return value` |
| Indentation | Shows which steps belong inside a construct |

#### **2.1.4 Analyzing Algorithms: Correctness and Efficiency**

Two algorithms for the same problem can behave very differently. Analysis answers two questions: **Is it correct?** and **How much does it cost?**

##### **Cost measures**

| Measure | Meaning |
| ----- | ----- |
| **Time complexity** | How the number of basic operations grows with the input size n |
| **Space complexity** | How much extra memory is needed as n grows |

Cost is measured by counting operations, not seconds, because seconds depend on the machine. **Big-O notation** keeps only the fastest-growing term and drops constant factors, so 3n² + 5n + 20 is O(n²).

**Counting example.** `FindMax` does one comparison per item after the first, so n − 1 comparisons: **O(n)** time, and it stores only a few variables: **O(1)** extra space.

##### **Common growth rates**

| Class | Name | Example algorithm |
| ----- | ----- | ----- |
| O(1) | Constant | Reading `array[i]` |
| O(log n) | Logarithmic | Binary search |
| O(n) | Linear | Linear search, find max |
| O(n log n) | Linearithmic | Merge sort |
| O(n²) | Quadratic | Bubble, selection, insertion sort |
| O(2ⁿ) | Exponential | Checking every subset of n items |
| O(n!) | Factorial | Trying every ordering of n cities |

##### **Why growth rate matters**

Operations needed (approximate), and running time at 10⁹ operations per second:

| n | log₂ n | n log₂ n | n² | 2ⁿ |
| ----- | ----- | ----- | ----- | ----- |
| 10 | 3 | 33 | 100 | 1,024 |
| 100 | 7 | 664 | 10,000 | about 1.3 × 10³⁰ |
| 1,000 | 10 | about 10,000 | 1,000,000 | about 10³⁰¹ |
| 1,000,000 | 20 | about 20 million | 10¹² | impossible |

For n = 1,000,000, an O(n log n) sort takes about **0.02 seconds** while an O(n²) sort takes about **1,000 seconds (roughly 17 minutes)**. For O(2ⁿ), even n = 100 would outlast the universe.

##### **Best, average and worst case**

| Case | Meaning | Example: linear search for a target |
| ----- | ----- | ----- |
| Best | The most favorable input | Target is the first item: 1 comparison |
| Average | A typical input | Target is somewhere in the middle: about n/2 comparisons |
| Worst | The least favorable input | Target is last or absent: n comparisons |

Worst-case analysis is the usual default because it gives a guarantee: the algorithm never does worse than this.

**Common misconceptions**

| Misconception | Reality |
| ----- | ----- |
| "O(n²) is always slower than O(n)." | Only for large enough n. For tiny inputs, constants can reverse the order |
| "Big-O gives exact running time." | It gives the growth trend, not seconds |
| "Time and space are the same." | They trade off: caching results saves time but uses memory |

### **2.2 Iteration and Recursion**

Both are ways to repeat work. Iteration repeats a block of steps with a **loop**; recursion solves a problem by calling **itself** on a smaller instance.

#### **Iteration**

| Loop | Behavior | Example |
| ----- | ----- | ----- |
| **Counted loop** (`for`) | Runs a known number of times | `for i in range(1, 6)` runs 5 times |
| **Conditional loop** (`while`) | Tests a condition before each pass; may run zero times | `while b != 0:` in Euclid's algorithm |
| **Post-test loop** (`do ... while`, in some languages) | Tests after each pass; runs at least once | Menu that shows at least once |

A **loop invariant** is a statement that is true before and after every pass. It is the main tool for proving a loop correct. In `FindMax`, the invariant is "`max` holds the largest of the items examined so far."

Pitfalls: **infinite loops** (the condition never becomes false), **off-by-one errors** (running one pass too many or too few), and forgetting to update the loop variable.

#### **Recursion**

A recursive function has two parts:

| Part | Role |
| ----- | ----- |
| **Base case** | A simple instance answered directly; it stops the recursion |
| **Recursive case** | Reduces the problem to a smaller instance of itself and combines the result |

```python
def factorial(n):
    if n == 0:                # base case
        return 1
    return n * factorial(n - 1)   # recursive case
```

**How it runs.** Each call is pushed onto the **call stack** with its own variables and waits until the call it made returns. For `factorial(4)`:

| Phase | What happens |
| ----- | ----- |
| Going down | factorial(4) → factorial(3) → factorial(2) → factorial(1) → factorial(0) |
| Base case | factorial(0) returns 1 |
| Coming back | factorial(1) = 1×1 = 1, factorial(2) = 2×1 = 2, factorial(3) = 3×2 = 6, factorial(4) = 4×6 = **24** |

**Rules for correct recursion:** every call must move toward the base case, and the base case must be reachable. A missing or unreachable base case ends in **stack overflow**. Python, for example, limits depth to 1,000 calls by default and does not optimize tail calls.

#### **Recursion that repeats work: Fibonacci**

```python
def fib(n):
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)
```

This is clear but slow: `fib(30)` makes about **2.7 million calls**, because the same values are recomputed again and again, giving **exponential** time. **Memoization** stores each result the first time it is computed:

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n):
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)
```

Now each value is computed once: **O(n)** time. This is the idea behind dynamic programming (see 2.4.1).

#### **A problem that is naturally recursive: Towers of Hanoi**

Move n disks from peg A to peg C using peg B, moving one disk at a time and never placing a larger disk on a smaller one.

```python
def hanoi(n, source, target, spare):
    if n == 0:
        return
    hanoi(n - 1, source, spare, target)       # move n-1 disks out of the way
    print(f"Move disk {n} from {source} to {target}")
    hanoi(n - 1, spare, target, source)       # move them onto the big disk
```

The number of moves is **2ⁿ − 1**: 7 moves for 3 disks, 1,023 for 10 disks, and about 1.8 × 10¹⁹ for 64 disks. Writing this with loops is much harder, which shows when recursion pays off.

#### **Types of recursion**

| Type | Meaning |
| ----- | ----- |
| Direct | A function calls itself |
| Indirect (mutual) | A calls B and B calls A |
| **Tail recursion** | The recursive call is the last action, so some compilers can reuse the stack frame |
| Multiple recursion | Several recursive calls per call (Fibonacci, tree traversal) |

#### **Iteration versus recursion**

| | Iteration | Recursion |
| ----- | ----- | ----- |
| Repeats by | Loop | Function calls |
| Extra memory | Usually O(1) | O(depth) call-stack frames |
| Speed | Usually slightly faster (no call overhead) | Call overhead; can repeat work if not memoized |
| Readability | Best for simple counting and scanning | Best for self-similar problems: trees, divide and conquer, backtracking |
| Failure mode | Infinite loop | Stack overflow |

**Equivalence:** any recursive algorithm can be rewritten with a loop and an explicit stack, and any loop can be written recursively. The choice is about clarity and resources, not power.

**Common misconceptions**

| Misconception | Reality |
| ----- | ----- |
| "Recursion is always slower and worse." | It can be the clearest way to express tree and divide-and-conquer algorithms |
| "Recursion uses no extra memory." | Every pending call occupies a stack frame |
| "The base case is optional." | Without it the recursion never terminates |
| "Memoization changes the answer." | It only avoids recomputation; results are identical |

### **2.3 Sorting and Searching**

#### **2.3.1 Basic Algorithms I: Searching**

**Searching** means finding the position of a target value in a collection, or reporting that it is absent.

##### **Linear (sequential) search**

Check each item in order until the target is found or the items run out.

```python
def linear_search(items, target):
    for i, value in enumerate(items):
        if value == target:
            return i
    return -1          # not found
```

* Works on **any** list, sorted or not.
* Time: O(n) worst case. Space: O(1).

##### **Binary search**

Requires a **sorted array**. Compare the target with the middle item; if equal, done; if the target is smaller, discard the upper half; if larger, discard the lower half. Repeat on the remaining half.

```python
def binary_search(items, target):
    low, high = 0, len(items) - 1
    while low <= high:
        mid = (low + high) // 2
        if items[mid] == target:
            return mid
        elif items[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return -1
```

* Time: **O(log n)**, because each step halves the range. Space: O(1) (iterative).
* Needs random access to the middle item, so it suits arrays rather than linked lists.

**Worked example.** Search for 23 in `[2, 5, 8, 12, 16, 23, 38, 56, 72, 91]` (indexes 0 to 9).

| Step | low | high | mid | items[mid] | Decision |
| ----- | ----- | ----- | ----- | ----- | ----- |
| 1 | 0 | 9 | 4 | 16 | 16 < 23, so low = 5 |
| 2 | 5 | 9 | 7 | 56 | 56 > 23, so high = 6 |
| 3 | 5 | 6 | 5 | 23 | Found at index 5 |

Three comparisons instead of up to ten.

##### **How much better is binary search?**

| Items n | Linear search (worst) | Binary search (worst) |
| ----- | ----- | ----- |
| 1,000 | 1,000 | 10 |
| 1,000,000 | 1,000,000 | 20 |
| 1,000,000,000 | 1,000,000,000 | 30 |

**Trade-off.** Binary search needs sorted data. Sorting costs O(n log n), so for a handful of lookups in unsorted data, linear search is cheaper; for many lookups, sort once and then use binary search. Another approach, the **hash table** (an extension beyond this outline), finds items in O(1) time on average by computing an index from the key.

**Common misconceptions**

| Misconception | Reality |
| ----- | ----- |
| "Binary search works on any list." | The data must be sorted |
| "Binary search is always the best choice." | If you search once in unsorted data, sorting first costs more than scanning |
| "mid = (low + high) / 2 never has problems." | In fixed-width integer languages, `low + high` can overflow; `low + (high − low) // 2` is safe |

#### **2.3.2 Basic Algorithms II: Sorting**

**Sorting** rearranges items into a defined order (numerically, alphabetically). It matters on its own and because it speeds up searching, merging and duplicate detection.

**Vocabulary**

| Term | Meaning |
| ----- | ----- |
| **Stable** | Items with equal keys keep their original relative order |
| **In-place** | Uses only O(1) (or O(log n)) extra memory |
| **Comparison sort** | Orders items only by comparing pairs; none can beat O(n log n) in the worst case |

Stability matters when sorting records by one field after another: sort students by name, then stably by grade, and students with equal grades stay in name order.

##### **Bubble sort**

Repeatedly step through the list, swapping adjacent items that are out of order. After each pass the largest remaining item "bubbles" to the end.

Trace on `[5, 2, 4, 1]`:

| Pass | Comparisons and swaps | List after the pass |
| ----- | ----- | ----- |
| 1 | (5,2) swap, (5,4) swap, (5,1) swap | 2, 4, 1, **5** |
| 2 | (2,4) ok, (4,1) swap | 2, 1, **4, 5** |
| 3 | (2,1) swap | **1, 2, 4, 5** |

* Time: O(n²) worst and average, O(n) best with an early-exit check when a pass makes no swaps. Space O(1). Stable.

##### **Selection sort**

Find the smallest item in the unsorted part and swap it into the next position of the sorted part.

Trace on `[29, 10, 14, 37, 13]`:

| Step | Smallest of the unsorted part | List after swap |
| ----- | ----- | ----- |
| 1 | 10 | **10**, 29, 14, 37, 13 |
| 2 | 13 | 10, **13**, 14, 37, 29 |
| 3 | 14 (already in place) | 10, 13, **14**, 37, 29 |
| 4 | 29 | 10, 13, 14, **29**, 37 |

* Time: O(n²) in all cases, but makes at most n − 1 swaps (good when writes are expensive). Space O(1). The usual array version is not stable.

##### **Insertion sort**

Grow a sorted prefix: take the next item and slide it left past larger items until it fits, as when sorting playing cards in your hand.

```python
def insertion_sort(a):
    for i in range(1, len(a)):
        key = a[i]
        j = i - 1
        while j >= 0 and a[j] > key:
            a[j + 1] = a[j]       # shift larger item right
            j -= 1
        a[j + 1] = key
    return a
```

Trace on `[5, 2, 4, 1]`:

| i | key | List after inserting the key |
| ----- | ----- | ----- |
| 1 | 2 | 2, 5, 4, 1 |
| 2 | 4 | 2, 4, 5, 1 |
| 3 | 1 | 1, 2, 4, 5 |

* Time: O(n²) worst and average, **O(n) on nearly sorted data**. Space O(1). Stable. Often used for small inputs and as the finishing step in faster hybrid sorts.

##### **Merge sort (divide and conquer)**

Split the list in half, sort each half recursively, then **merge** the two sorted halves by repeatedly taking the smaller front item.

```python
def merge_sort(a):
    if len(a) <= 1:
        return a
    mid = len(a) // 2
    left, right = merge_sort(a[:mid]), merge_sort(a[mid:])
    merged, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:            # <= keeps equal items in order (stable)
            merged.append(left[i]); i += 1
        else:
            merged.append(right[j]); j += 1
    return merged + left[i:] + right[j:]
```

Trace on `[38, 27, 43, 3, 9, 82]`:

| Stage | State |
| ----- | ----- |
| Split | [38, 27, 43] and [3, 9, 82] |
| Split further | [38], [27, 43] and [3], [9, 82] |
| Merge small | [27, 43] and [9, 82] |
| Merge to halves | [27, 38, 43] and [3, 9, 82] |
| Final merge | **[3, 9, 27, 38, 43, 82]** |

* Time: **O(n log n) in every case** (log n levels of splitting, n work per level). Space: O(n). Stable. Well suited to linked lists and to data too large for memory.

##### **Quick sort (divide and conquer)**

Choose a **pivot**, partition the list so smaller items come before it and larger after, then sort each side recursively (Hoare, 1962).

Partition of `[8, 3, 1, 7, 0, 10, 2]` with the last item (2) as pivot, scanning left to right and moving items ≤ pivot to the front:

| Step | List | Note |
| ----- | ----- | ----- |
| Start | 8, 3, 1, 7, 0, 10, **2** | pivot = 2 |
| After scan | 1, 0, 8, 7, 3, 10, **2** | 1 and 0 (≤ 2) moved to the front |
| Place pivot | 1, 0, **2**, 7, 3, 10, 8 | 2 is now in its final position |

Then quick sort `[1, 0]` and `[7, 3, 10, 8]` recursively.

* Time: O(n log n) on average, **O(n²) worst case** (for example, always picking the smallest or largest item as the pivot on sorted data). Choosing a random or median-of-three pivot makes the worst case rare. Space: O(log n) for the recursion stack. Usually not stable. Often the fastest in practice because it works in place with good memory access.

##### **Comparison**

| Algorithm | Best | Average | Worst | Extra space | Stable? | Notes |
| ----- | ----- | ----- | ----- | ----- | ----- | ----- |
| Bubble | O(n) | O(n²) | O(n²) | O(1) | Yes | Teaching only |
| Selection | O(n²) | O(n²) | O(n²) | O(1) | No | Few swaps |
| Insertion | O(n) | O(n²) | O(n²) | O(1) | Yes | Best for small or nearly sorted data |
| Merge | O(n log n) | O(n log n) | O(n log n) | O(n) | Yes | Guaranteed speed |
| Quick | O(n log n) | O(n log n) | O(n²) | O(log n) | No | Fast in practice |
| Heap | O(n log n) | O(n log n) | O(n log n) | O(1) | No | Uses a heap (see 2.8.2) |

Beyond comparison sorts, **counting sort** runs in O(n + k) when keys are small integers in a range of size k.

**Common misconceptions**

| Misconception | Reality |
| ----- | ----- |
| "Quick sort is always O(n log n)." | Its worst case is O(n²) |
| "The fastest sort is best for every job." | Stability, memory and input size also matter |
| "Bubble sort is used in real systems." | It is mainly a teaching example |

### **2.4 Algorithm Design Strategies and Limits**

#### **2.4.1 Algorithm Design Strategies**

"Basic algorithms (sorting, searching, etc.)" is easier to remember as a small set of general strategies.

| Strategy | Idea | Examples |
| ----- | ----- | ----- |
| **Brute force** | Try every possibility | Linear search, checking all subsets |
| **Divide and conquer** | Split into smaller subproblems, solve each, combine | Binary search, merge sort, quick sort |
| **Greedy** | At each step take the locally best choice | Dijkstra's shortest paths, Huffman coding, making change with standard coins |
| **Dynamic programming** | Solve overlapping subproblems once and store the answers | Memoized Fibonacci, knapsack, edit distance |
| **Backtracking** | Build a solution step by step and undo a step when it cannot work | N-queens, Sudoku, maze solving |

**Greedy does not always work.** Make change for 6 using coins {1, 3, 4}. Greedy takes 4, then 1, then 1: **3 coins**. The optimal answer is 3 + 3: **2 coins**. Greedy is correct only for problems with the right structure (for standard coin systems such as 1, 5, 10, 25 it is).

#### **2.4.2 Limits and Challenges of Algorithms**

| Challenge | What it means |
| ----- | ----- |
| **Intractable problems** | Problems with no known efficient algorithm. Brute-forcing the traveling salesman problem over 20 cities means checking about (19!)/2 ≈ 6 × 10¹⁶ routes |
| **Undecidable problems** | No algorithm can solve them in general (the halting problem) |
| **Correctness** | Subtle bugs: boundary cases, off-by-one errors, empty input |
| **Trade-offs** | Time versus memory, simplicity versus speed, average versus worst case |
| **Heuristics and approximation** | For hard problems, accept a good but not always optimal answer (as in the search methods used in symbolic AI planning) |

#### **2.4.3 Summary of the Algorithm Subtopics**

| Topic | Key idea |
| ----- | ----- |
| Algorithm | Finite, precise, effective procedure from input to output |
| Features | Input, output, finiteness, definiteness, effectiveness (plus correctness, generality) |
| Representation | Natural language, flowchart, pseudocode, code; built from sequence, selection, iteration |
| Efficiency | Big-O describes growth of time and space with input size |
| Searching | Linear O(n) on any data; binary O(log n) on sorted arrays |
| Sorting | Simple sorts O(n²); merge sort O(n log n) guaranteed; quick sort fast on average |
| Iteration vs recursion | Loops use constant memory; recursion needs a base case and uses the call stack |

### **2.5 Data Structures: Overview, Arrays and Records**

#### **2.5.1 Overview**

A **data structure** is a way of organizing, storing and accessing data so that operations on it are efficient. An **abstract data type (ADT)** describes *what* a structure does (its operations) without saying *how* it is built. A stack, for example, is an ADT with `push` and `pop`; it can be implemented with an array or a linked list.

**Classification**

| Category | Examples | Shape |
| ----- | ----- | ----- |
| **Linear** | Array, linked list, stack, queue | Items in a sequence, each with one predecessor and one successor |
| **Non-linear** | Tree, graph | Items connected in a hierarchy or network |
| **Composite** | Record | Groups fields of different types |

| Static | Dynamic |
| ----- | ----- |
| Size fixed at creation (classic arrays) | Size changes at run time (linked lists, resizable arrays) |

**Choosing a structure.** Ask: which operations are most frequent (access by position, search, insert, delete)? Is the order important? How large will it grow? The answer decides the structure.

#### **2.5.2 Arrays**

An **array** stores a fixed number of elements of the **same type** in **consecutive memory locations**, each identified by an **index** (usually starting at 0).

```
index:   0     1     2     3     4
value: [ 10 ] [ 20 ] [ 30 ] [ 40 ] [ 50 ]
```

**Why access is instant.** The address of element i is

**address = base address + i × element size**

so the computer jumps straight to any element without scanning. That is **O(1) random access**.

**Two-dimensional arrays** (tables, images) are stored row by row (row-major order): for a table with `cols` columns, element (i, j) is at base + (i × cols + j) × element size.

**Operations and cost**

| Operation | Cost | Why |
| ----- | ----- | ----- |
| Access `a[i]` | O(1) | Address arithmetic |
| Search (unsorted) | O(n) | Must scan |
| Search (sorted) | O(log n) | Binary search |
| Insert or delete at the end | O(1) (amortized when resizing) | No shifting |
| Insert or delete in the middle or at the front | O(n) | Following items must shift |

**Worked example: insert 25 at index 2** of `[10, 20, 30, 40, 50]` in an array with spare room:

| Step | Array |
| ----- | ----- |
| Start | 10, 20, 30, 40, 50, _ |
| Shift 50 right | 10, 20, 30, 40, _, 50 |
| Shift 40 right | 10, 20, 30, _, 40, 50 |
| Shift 30 right | 10, 20, _, 30, 40, 50 |
| Write 25 | 10, 20, **25**, 30, 40, 50 |

Three shifts for a six-element array; for a million elements it could be a million.

**Dynamic arrays** (Python `list`, Java `ArrayList`, C++ `vector`) hide a fixed array. When it fills, they allocate a larger one (typically about double), copy the items, and continue. Because resizes are rare, appending is **O(1) on average (amortized)**.

**Strengths and limitations**

| Strengths | Limitations |
| ----- | ----- |
| Instant access by index | Fixed size (static arrays) |
| Compact: no per-element overhead | Inserting and deleting in the middle is slow |
| Fast sequential scanning because items sit side by side in memory | Needs a contiguous block of memory |
| Simple, supported by every language | All elements must be the same type |

**Applications:** lists of scores, pixel grids, lookup tables, the storage behind stacks, queues, heaps and hash tables.

**Common misconceptions:** "Arrays start at 1" (in most languages they start at 0, a frequent source of off-by-one errors). "Python lists are linked lists" (they are dynamic arrays). Accessing an index beyond the end is an error in safe languages and a security hole (buffer overflow) in languages like C.

#### **2.5.3 Records**

A **record** (also called a **struct**, **tuple**, or **object**) groups a fixed set of **named fields**, which may have **different types**, into one unit that describes a single entity.

```c
struct Student {
    int   id;
    char  name[30];
    float gpa;
};
```

```python
from dataclasses import dataclass

@dataclass
class Student:
    student_id: int
    name: str
    gpa: float

s = Student(1, "Ana", 3.8)
print(s.name)          # Ana
```

**Array versus record**

| | Array | Record |
| ----- | ----- | ----- |
| Elements | Same type | Can be different types |
| Access by | Numeric index | Field name |
| Size | Usually grows with the number of items | Fixed set of fields |
| Typical use | Many similar items | One thing with several properties |

**Arrays of records** combine the two: an array of 500 `Student` records is a small table, where each record is a row and each field a column. This is exactly the shape of a database table (1 row = 1 record) and of the CSV files used in data work.

**Operations:** create, read a field (O(1), the field's position is fixed), update a field, copy. Nested records are allowed (a `Student` containing an `Address` record).

**Notes**

* In memory, compilers may insert **padding** between fields so each starts at a suitable address, so a record can be larger than the sum of its fields.
* Records are the foundation of **objects** in object-oriented programming, which add behavior (methods) to the fields.
* When sorting an array of records, the sort uses one field as the **key**; a stable sort keeps records with equal keys in their original order.

**Strengths and limitations**

| Strengths | Limitations |
| ----- | ----- |
| Models real-world entities naturally | Fixed structure: adding a field changes the type |
| Readable named access | One record describes one entity only; collections need arrays or lists |
| Mixes data types | Searching a collection of records still needs an array, list or index |

**Applications:** student, customer or product entries; configuration settings; nodes of linked lists and trees (each node is a record holding a value and references).

### **2.6 Linked Lists**

A **linked list** is a chain of **nodes**. Each node is a record holding a **value** and a **reference (pointer)** to the next node. The list is accessed through its **head**; the last node points to nothing (`null`).

```
head → [ 7 | • ] → [ 12 | • ] → [ 5 | • ] → [ 9 | null ]
```

**Variants**

| Type | Description | Benefit |
| ----- | ----- | ----- |
| **Singly linked** | Each node has `next` | Simple, least memory |
| **Doubly linked** | Each node has `next` and `prev` | Traverse both ways; delete a known node in O(1) |
| **Circular** | The last node points back to the first | Round-robin scheduling, repeating playlists |

**Operations and cost (singly linked, with only a head pointer)**

| Operation | Cost | Why |
| ----- | ----- | ----- |
| Access the k-th item | O(k), so O(n) | Must follow links from the head |
| Search | O(n) | Walk the chain |
| Insert at the head | O(1) | Change two references |
| Insert after a known node | O(1) | Change two references |
| Delete the head | O(1) | Move the head |
| Delete a given node | O(n) (needs the previous node); O(1) if doubly linked | |
| Insert at the end | O(n), or O(1) with a tail pointer | |

**Worked example: insert 8 after the node holding 12** in `7 → 12 → 5 → 9`:

1. Create a new node holding 8.
2. Set the new node's `next` to the node holding 5.
3. Set the node 12's `next` to the new node.

Result: `7 → 12 → 8 → 5 → 9`. No element was shifted. (If step 3 were done before step 2, the rest of the list would be lost; **order matters**.)

```python
class Node:
    def __init__(self, value):
        self.value = value
        self.next = None

class LinkedList:
    def __init__(self):
        self.head = None

    def push_front(self, value):
        node = Node(value)
        node.next = self.head
        self.head = node

    def find(self, value):
        cur = self.head
        while cur is not None:
            if cur.value == value:
                return cur
            cur = cur.next
        return None

    def reverse(self):
        prev, cur = None, self.head
        while cur is not None:
            nxt = cur.next       # remember the rest
            cur.next = prev      # flip the link
            prev = cur
            cur = nxt
        self.head = prev
```

Trace of `reverse()` on `1 → 2 → 3`: the loop flips each link in turn and ends with `3 → 2 → 1`.

**Array versus linked list**

| | Array | Linked list |
| ----- | ----- | ----- |
| Access by position | O(1) | O(n) |
| Insert or delete in the middle | O(n) (shifting) | O(1) once the position is found |
| Memory | Compact, contiguous | Extra pointer per node; nodes scattered in memory |
| Size | Fixed or occasionally resized | Grows one node at a time |
| Sequential scan speed | Fast (items adjacent) | Slower (follow pointers) |
| Best when | Reads by index dominate | Frequent insertions and deletions at known positions |

**Strengths and limitations**

| Strengths | Limitations |
| ----- | ----- |
| Flexible size, no resizing or copying | No fast random access |
| Cheap insertion and deletion at known positions | Extra memory for pointers |
| Easy to splice lists together | Pointer bugs (lost nodes, loops) are easy to make |

**Applications:** undo history, music playlists, memory management of free blocks, chaining in hash tables, building blocks for stacks and queues.

**Common misconceptions:** "Linked lists are always faster for insertion." Finding the position still costs O(n), so inserting in the middle by value is O(n) in both structures. In practice arrays win on many real workloads because of memory locality.

### **2.7 Stacks and Queues**

#### **2.7.1 Stacks**

A **stack** is a collection with **last-in, first-out (LIFO)** order: only the top is accessible. Think of a stack of plates.

| Operation | Meaning | Cost |
| ----- | ----- | ----- |
| `push(x)` | Place x on top | O(1) |
| `pop()` | Remove and return the top | O(1) |
| `peek()` / `top()` | Read the top without removing it | O(1) |
| `isEmpty()` | Is the stack empty? | O(1) |

**Errors:** **overflow** (pushing onto a full fixed-size stack) and **underflow** (popping an empty stack).

**Implementation:** an array with a `top` index, or a linked list where `push` and `pop` work at the head. In Python, a list works: `append` is push and `pop()` is pop.

**Worked example: push and pop.**

| Operation | Stack (bottom → top) | Returned |
| ----- | ----- | ----- |
| push(1) | 1 | |
| push(2) | 1, 2 | |
| push(3) | 1, 2, 3 | |
| pop() | 1, 2 | 3 |
| peek() | 1, 2 | 2 |
| pop() | 1 | 2 |

**Application 1: the call stack.** Every function call pushes a frame; returning pops it. This is why deep recursion (2.2) can overflow the stack.

**Application 2: balanced brackets.** Push every opening bracket; on a closing bracket, pop and check it matches. The text is balanced if no mismatch occurs and the stack ends empty.

| Input | Process | Result |
| ----- | ----- | ----- |
| `{[()]}` | Push `{`, `[`, `(`; `)` pops `(` ok; `]` pops `[` ok; `}` pops `{` ok; stack empty | Balanced |
| `{[(])}` | Push `{`, `[`, `(`; `]` pops `(` which does not match `[` | Not balanced |

```python
def balanced(text):
    pairs = {")": "(", "]": "[", "}": "{"}
    stack = []
    for ch in text:
        if ch in "([{":
            stack.append(ch)
        elif ch in pairs:
            if not stack or stack.pop() != pairs[ch]:
                return False
    return not stack
```

**Application 3: evaluating postfix expressions.** In postfix notation the operator follows its operands, so no parentheses are needed. Push numbers; on an operator, pop two, apply it, push the result. Evaluate `5 3 + 8 2 - *` (which means (5 + 3) × (8 − 2)):

| Token | Action | Stack (bottom → top) |
| ----- | ----- | ----- |
| 5 | push | 5 |
| 3 | push | 5, 3 |
| + | pop 3 and 5, push 5 + 3 | 8 |
| 8 | push | 8, 8 |
| 2 | push | 8, 8, 2 |
| − | pop 2 and 8, push 8 − 2 | 8, 6 |
| * | pop 6 and 8, push 8 × 6 | **48** |

**Other uses:** undo and redo, the browser Back button, depth-first search and backtracking (Sudoku, mazes), converting infix to postfix.

**Strengths and limitations:** very simple and fast (O(1) operations), but access is restricted to the top; searching or reaching deeper items means popping others.

#### **2.7.2 Queues**

A **queue** is a collection with **first-in, first-out (FIFO)** order: items are added at the **rear** and removed from the **front**, like a line at a ticket counter.

| Operation | Meaning | Cost |
| ----- | ----- | ----- |
| `enqueue(x)` | Add x at the rear | O(1) |
| `dequeue()` | Remove and return the front item | O(1) |
| `front()` / `peek()` | Read the front item | O(1) |
| `isEmpty()` | Is the queue empty? | O(1) |

**Worked example.**

| Operation | Queue (front → rear) | Returned |
| ----- | ----- | ----- |
| enqueue(A) | A | |
| enqueue(B) | A, B | |
| enqueue(C) | A, B, C | |
| dequeue() | B, C | A |
| enqueue(D) | B, C, D | |
| dequeue() | C, D | B |

**Implementations**

* **Linked list** with head (front) and tail (rear) pointers: both operations O(1).
* **Circular array:** a fixed array where `front` and `rear` indexes wrap around using `rear = (rear + 1) mod capacity`, so freed space at the start is reused. This avoids the cost of shifting all items after each dequeue.
* **Warning:** removing from the front of a plain Python list is O(n). Use `collections.deque`, which supports O(1) operations at both ends.

```python
from collections import deque

q = deque()
q.append("A")      # enqueue
q.append("B")
q.append("C")
print(q.popleft()) # dequeue -> A
```

**Variants**

| Variant | Description | Use |
| ----- | ----- | ----- |
| **Circular queue** | Fixed-size queue with wrap-around indexes | Buffers (keyboard, network packets) |
| **Deque** (double-ended queue) | Add and remove at both ends | Sliding windows, undo with limits |
| **Priority queue** | Items leave by priority, not arrival order (usually implemented with a heap, see 2.8.2) | Operating-system scheduling, shortest-path algorithms |

**Applications:** print spoolers, task and CPU scheduling, call-center lines, message buffers, and **breadth-first search** (2.9).

**Stack versus queue**

| | Stack | Queue |
| ----- | ----- | ----- |
| Order | LIFO | FIFO |
| Add at | Top | Rear |
| Remove from | Top | Front |
| Typical use | Undo, recursion, backtracking | Scheduling, buffering, breadth-first search |

### **2.8 Trees and Binary Trees**

#### **2.8.1 Trees**

A **tree** is a **hierarchical**, non-linear structure of **nodes** connected by **edges**, with one special **root** at the top and **no cycles**. Every node except the root has exactly one **parent**.

**Terminology** (using this tree: A is the root with children B, C, D; B has children E and F; D has child G)

```
        A
     /  |  \
    B   C   D
   / \       \
  E   F       G
```

| Term | Meaning | In the example |
| ----- | ----- | ----- |
| **Root** | Top node, no parent | A |
| **Parent / child** | A node and the nodes directly below it | A is parent of B, C, D |
| **Siblings** | Nodes with the same parent | B, C, D |
| **Leaf** | Node with no children | E, F, C, G |
| **Internal node** | Node with at least one child | A, B, D |
| **Degree** | Number of children of a node | A has degree 3 |
| **Depth** of a node | Edges from the root to it | E has depth 2 |
| **Height** of a tree | Edges on the longest root-to-leaf path | 2 |
| **Subtree** | A node together with all its descendants | The subtree rooted at B holds B, E, F |
| **Path** | A sequence of connected nodes | A → B → F |

**Key properties:** a tree with n nodes has exactly **n − 1 edges**; there is exactly one path between any two nodes.

**Representation:** each node is a record holding a value and references to its children (a list of children, or "first child / next sibling" links).

**Traversals** visit every node once:

| Traversal | Order | Result on the tree above |
| ----- | ----- | ----- |
| **Pre-order** (depth-first) | Node, then children left to right | A, B, E, F, C, D, G |
| **Post-order** (depth-first) | Children left to right, then node | E, F, B, C, G, D, A |
| **Level-order** (breadth-first) | Level by level, using a queue | A, B, C, D, E, F, G |

Pre- and post-order are naturally written with recursion (2.2); level-order uses a queue (2.7.2).

**Applications**

| Area | Tree |
| ----- | ----- |
| Operating systems | File-system directories (folders contain files and folders) |
| Web | The HTML document tree (DOM) |
| Organizations | Org charts, taxonomies (biological classification) |
| Languages | Parse trees and expression trees (compilers, the sentence parse trees in NLP) |
| AI | Decision trees, game trees (minimax) |
| Databases | Index structures (B-trees, see 2.8.2) |

**Strengths and limitations**

| Strengths | Limitations |
| ----- | ----- |
| Models hierarchies naturally | More complex to implement than linear structures |
| Can give fast search, insertion and deletion (balanced search trees) | An unbalanced tree can be as slow as a list |
| Many problems are recursive on trees | Needs extra memory for references |

#### **2.8.2 Binary Trees**

A **binary tree** is a tree in which every node has **at most two children**, called the **left child** and the **right child**.

```python
class TreeNode:
    def __init__(self, key):
        self.key = key
        self.left = None
        self.right = None
```

**Shapes**

| Type | Definition |
| ----- | ----- |
| **Full** | Every node has 0 or 2 children |
| **Perfect** | Full, and all leaves are on the same level |
| **Complete** | All levels are full except possibly the last, which is filled left to right |
| **Balanced** | The heights of the two subtrees of every node differ by at most a small constant |
| **Degenerate (skewed)** | Every node has one child, so the tree is really a linked list |

**Useful properties** (height counted in edges, root at height 0)

| Fact | Formula |
| ----- | ----- |
| Maximum nodes at level i | 2ⁱ |
| Nodes in a perfect tree of height h | 2^(h+1) − 1 |
| Minimum height of a tree with n nodes | ⌊log₂ n⌋ |
| Height range for n nodes | from about log₂ n (balanced) up to n − 1 (degenerate) |

A balanced tree with 1,000,000 nodes has a height of only about **19**.

**Array representation of a complete binary tree.** Store nodes level by level; for the node at index i (starting at 0), its children are at **2i + 1** and **2i + 2** and its parent is at **(i − 1) // 2**. No pointers are needed.

##### **Traversals of a binary tree**

Four orders, defined recursively:

| Traversal | Order |
| ----- | ----- |
| **Pre-order** | Node, left subtree, right subtree |
| **In-order** | Left subtree, node, right subtree |
| **Post-order** | Left subtree, right subtree, node |
| **Level-order** | One level at a time, left to right (a queue) |

**Worked example.** The tree built by inserting 8, 3, 10, 1, 6, 14, 4, 7, 13 in a binary search tree:

```
          8
        /   \
       3     10
      / \      \
     1   6      14
        / \     /
       4   7   13
```

| Traversal | Result |
| ----- | ----- |
| Pre-order | 8, 3, 1, 6, 4, 7, 10, 14, 13 |
| **In-order** | **1, 3, 4, 6, 7, 8, 10, 13, 14** (sorted!) |
| Post-order | 1, 4, 7, 6, 3, 13, 14, 10, 8 |
| Level-order | 8, 3, 10, 1, 6, 14, 4, 7, 13 |

##### **Binary search trees (BST)**

A **binary search tree** keeps keys ordered: for every node, **all keys in its left subtree are smaller and all keys in its right subtree are larger**. That makes searching like binary search.

**Search:** start at the root; if the target equals the key, done; if smaller go left; if larger go right; reaching `null` means absent.

**Insert:** search for the key; when you reach `null`, attach the new node there.

**Delete** has three cases:

| Case | Action |
| ----- | ----- |
| Node is a leaf | Remove it |
| Node has one child | Replace the node by its child |
| Node has two children | Replace its key with its **in-order successor** (the smallest key in the right subtree), then delete that successor |

Example: deleting 3 from the tree above (two children, 1 and 6): the in-order successor is 4, so 4 takes 3's place and the old 4 leaf is removed.

```python
def insert(root, key):
    if root is None:
        return TreeNode(key)
    if key < root.key:
        root.left = insert(root.left, key)
    elif key > root.key:
        root.right = insert(root.right, key)
    return root

def search(root, key):
    while root is not None and root.key != key:
        root = root.left if key < root.key else root.right
    return root

def inorder(root):
    if root:
        yield from inorder(root.left)
        yield root.key
        yield from inorder(root.right)

root = None
for k in [8, 3, 10, 1, 6, 14, 4, 7, 13]:
    root = insert(root, k)
print(list(inorder(root)))     # [1, 3, 4, 6, 7, 8, 10, 13, 14]
```

**Cost of BST operations** (h = tree height)

| Operation | Cost | Balanced (h ≈ log n) | Degenerate (h = n − 1) |
| ----- | ----- | ----- | ----- |
| Search, insert, delete | O(h) | O(log n) | O(n) |
| In-order traversal | O(n) | O(n) | O(n) |

Inserting already-sorted keys (1, 2, 3, ...) produces a degenerate tree, so a plain BST gives no guarantee.

##### **Keeping trees balanced**

| Structure | Idea |
| ----- | ----- |
| **AVL tree** | After each insert or delete, rotate nodes so subtree heights differ by at most 1 (Adelson-Velsky and Landis, 1962) |
| **Red-black tree** | Color nodes and apply rules that keep the longest path at most twice the shortest; used in many library maps and sets |
| **B-tree** | A multi-way balanced tree with many keys per node, designed for disks; used in databases and file systems (Bayer and McCreight, 1972) |

##### **Heaps and priority queues**

A **binary heap** is a **complete** binary tree stored in an array that obeys the **heap property**: in a *min-heap* every parent is less than or equal to its children (the reverse for a max-heap), so the smallest item is always at the root.

| Operation | Method | Cost |
| ----- | ----- | ----- |
| Peek minimum | Read the root | O(1) |
| Insert | Add at the end, **sift up** while smaller than the parent | O(log n) |
| Extract minimum | Replace the root with the last item, **sift down** | O(log n) |
| Build from n items | Sift down from the middle of the array | O(n) |

Heaps implement **priority queues** (2.7.2) and **heap sort** (2.3.2).

**Other applications of binary trees:** expression trees (the expression (3 + 4) × 5 has × at the root, + and 5 as its children, and 3 and 4 below +; in-order gives the expression, post-order gives postfix `3 4 + 5 *`), **Huffman coding** for compression, decision trees, and routing tables.

**Strengths and limitations**

| Strengths | Limitations |
| ----- | ----- |
| BST search, insert and delete in O(log n) when balanced | Plain BST can degrade to O(n) |
| Ordered traversal for free (in-order) | Balancing adds complexity |
| Flexible size | Slower than arrays or hash tables for pure lookup by index or key |
| Heaps give O(1) access to the minimum | A heap is not good for searching arbitrary keys |

**Common misconceptions**

| Misconception | Reality |
| ----- | ----- |
| "A binary tree is a binary search tree." | A BST also requires the ordering property |
| "BST search is always O(log n)." | Only if the tree is balanced |
| "A heap is a sorted array." | It is only partially ordered; the smallest is at the root, but siblings are not ordered |
| "Binary trees must have two children per node." | At most two; leaves have none |

### **2.9 Graphs**

This added subtopic completes the picture, because breadth-first and depth-first search build directly on queues and stacks. A **graph** G = (V, E) is a set of **vertices** (nodes) and **edges** connecting pairs of them. Unlike a tree, a graph may contain cycles and have no root. Edges can be **directed** or **undirected**, and **weighted** or not. A tree is a connected graph with no cycles.

**Representations**

| Representation | Idea | Space | Edge check | Best for |
| ----- | ----- | ----- | ----- | ----- |
| **Adjacency matrix** | V × V table: 1 if there is an edge | O(V²) | O(1) | Dense graphs |
| **Adjacency list** | For each vertex, a list of its neighbors | O(V + E) | O(degree) | Sparse graphs |

<img width="50%" height="50%" alt="image" src="https://github.com/user-attachments/assets/f7adaed0-5953-4e1b-bd6b-1e6db48716a7" />
</div>

**Traversals**

| | Breadth-first search (BFS) | Depth-first search (DFS) |
| ----- | ----- | ----- |
| Order | Level by level from the start | As deep as possible, then backtrack |
| Data structure | **Queue** | **Stack** (or recursion) |
| Time | O(V + E) | O(V + E) |
| Finds | Fewest-edge path in unweighted graphs | Cycles, connected components, topological order |

Graph: edges A–B, A–C, B–D, C–E. Starting at A and visiting neighbors in alphabetical order:

| Search | Visit order |
| ----- | ----- |
| BFS | A, B, C, D, E |
| DFS | A, B, D, C, E |

```python
from collections import deque

graph = {"A": ["B", "C"], "B": ["A", "D"], "C": ["A", "E"],
         "D": ["B"], "E": ["C"]}

def bfs(start):
    visited, order = {start}, []
    queue = deque([start])
    while queue:
        node = queue.popleft()
        order.append(node)
        for nb in graph[node]:
            if nb not in visited:
                visited.add(nb)
                queue.append(nb)
    return order

print(bfs("A"))        # ['A', 'B', 'C', 'D', 'E']
```

For weighted graphs, **Dijkstra's algorithm** (1959) finds shortest paths using a priority queue (a heap).

**Applications:** road and route maps, social networks, the web's links, dependency graphs, and state spaces in AI search.

### **2.10 Choosing a Data Structure, Practice and Summary**

#### **2.10.1 Comparison and Choosing a Data Structure**

**Cost of common operations**

| Structure | Access by position | Search | Insert | Delete | Notes |
| ----- | ----- | ----- | ----- | ----- | ----- |
| Array | O(1) | O(n); O(log n) if sorted | O(n) (O(1) at the end, amortized) | O(n) | Contiguous, compact |
| Linked list | O(n) | O(n) | O(1) at a known position | O(1) at a known position (doubly linked) | Flexible size |
| Stack | top only | O(n) | O(1) push | O(1) pop | LIFO |
| Queue | front only | O(n) | O(1) enqueue | O(1) dequeue | FIFO |
| Balanced BST | not by position | O(log n) | O(log n) | O(log n) | Ordered keys |
| Heap | min or max only | O(n) | O(log n) | O(log n) (extract) | Priority access |
| Hash table (extension) | by key | O(1) average | O(1) average | O(1) average | No ordering |

**Which one to use**

| Need | Choose |
| ----- | ----- |
| Fast access by index, fixed or slowly growing data | Array (dynamic array) |
| Many insertions and deletions in the middle at known positions | Linked list |
| Undo, backtracking, matching brackets, recursion | Stack |
| Fair processing in arrival order, buffering | Queue |
| Ordered data with fast search and insert | Balanced binary search tree |
| Repeatedly get the smallest or largest item | Heap (priority queue) |
| Hierarchies (folders, organization charts) | Tree |
| Networks and connections | Graph |
| A record of one thing with several attributes | Record |

#### **2.10.3 Summary of the Data Structure Subtopics**

| Structure | Core idea | Key strength | Key weakness |
| ----- | ----- | ----- | ----- |
| Array | Same-type items in contiguous memory | O(1) access by index | Slow middle insert and delete |
| Record | Named fields of mixed types | Models one entity | Fixed layout |
| Linked list | Nodes linked by references | Cheap insert and delete at a known place | O(n) access |
| Stack | LIFO | Simple, O(1) push and pop | Only the top is reachable |
| Queue | FIFO | Fair ordering, O(1) operations | Only the ends are reachable |
| Tree | Hierarchy of nodes | Natural for nested data | More complex |
| Binary tree / BST | At most two children; BST keeps order | O(log n) search when balanced | Degenerates if unbalanced |
| Heap | Complete tree with heap property | O(1) min or max | Poor for general search |
