## **1. Introduction to Symbolic AI**

### **1.1 What Symbolic AI Is**

#### **1.1.1 Definition**

**Symbolic AI** is the approach to artificial intelligence in which knowledge is written down explicitly as **symbols, rules, and logic**, and the computer reasons by manipulating those symbols. It is also called **GOFAI (Good Old-Fashioned AI)** and was the dominant approach from the 1950s to the 1980s.

#### **1.1.2 Core Idea: Representation and Manipulation of Symbols**

The idea has two parts:

1. **Representation.** Facts about the world are encoded as symbols a computer can store. For example, `Human(Socrates)` or “fever” and “cough”.
2. **Manipulation.** The computer applies logical rules to those symbols to produce new knowledge.

The classic example:

* Fact: `Human(Socrates)`
* Rule: `∀x (Human(x) → Mortal(x))`
* Conclusion: `Mortal(Socrates)`

Nobody trained the system on examples. It reached the conclusion by following rules, the way a person works through a proof. The underlying belief is that human thinking is largely symbol manipulation, so a machine that does the same can behave intelligently.

#### **1.1.3 Contrast with Sub-Symbolic AI (Connectionist/Neural)**

|  | Symbolic AI | Sub-symbolic AI |
| ----- | ----- | ----- |
| Knowledge is stored as | Explicit rules, logic, symbols | Numerical weights in a network |
| Where knowledge comes from | Written by humans | Learned from data |
| Reasoning | Step-by-step logical inference | Pattern recognition |
| Explainability | High; you can trace each step | Low; often a “black box” |
| Handles noisy or uncertain data | Poorly | Well |
| Typical examples | Expert systems, theorem provers | Neural networks, deep learning, LLMs |

**In short, symbolic AI is told what to know, while sub-symbolic AI learns what to know.**

#### **1.1.4 Goal of Symbolic AI**

The goal is to build systems that can **reason, make decisions, and solve problems** using human-readable knowledge, and to **explain** how they reached a conclusion. It aims to capture expert knowledge (a doctor’s diagnostic rules, for example) so a machine can apply it consistently.

### **1.2 History**

* **1956:** The Dartmouth Conference names the field “artificial intelligence.” The **Logic Theorist** (Newell, Simon, Shaw) proves mathematical theorems.
* **1957:** The **General Problem Solver (GPS)** attempts general-purpose problem solving.
* **1958:** John McCarthy creates **LISP**, the main AI language for decades.
* **1960s:** Early rule-based programs appear, such as **ELIZA** (pattern-matching chatbot) and **DENDRAL** (infers chemical structures).
* **1970s:** **MYCIN** diagnoses blood infections with roughly hundreds of if-then rules. Minsky proposes **frames** for knowledge representation, and **Prolog** appears (1972), a logic programming language.
* **1980s:** The **expert systems boom**. Companies deploy systems like XCON, which configured computer orders for DEC.
* **Late 1980s to 1990s:** Expert systems prove costly to maintain and brittle, and funding collapses (the **AI winter**). Machine learning takes over.
* **Today:** Symbolic ideas survive in knowledge graphs, planning, and **neuro-symbolic AI**.

### **1.3 How Symbolic AI Works (in General)**

A symbolic system has three main parts:

1. **Knowledge base:** the stored facts and rules.
2. **Inference engine:** the reasoning program that applies rules to facts to derive conclusions.
3. **Interface:** how users enter facts and receive answers, often with an explanation.

**Worked example (from your lecture slides):**
`IF fever AND cough AND difficulty breathing THEN possible pneumonia`

1. The user reports symptoms (new facts).
2. The inference engine checks which rules match.
3. The pneumonia rule fires, and the conclusion “possible pneumonia” is added.
4. The system can show the rule that led there.

Two reasoning styles are worth knowing:

* **Forward chaining:** start from known facts and move toward conclusions.
* **Backward chaining:** start from a hypothesis (such as “pneumonia?”) and check whether the facts support it.

### **1.4 Strengths and Limitations, Explained**

**Strengths**

* **Interpretability:** every conclusion traces to specific rules, which matters in medicine, law, and finance.
* **Structured knowledge:** complex domain knowledge can be formalized clearly.
* **Flexibility:** you change behavior by editing rules, with no retraining.

**Limitations**

* **Incomplete knowledge:** if a rule is missing, the system fails rather than guessing.
* **Scalability:** thousands of interacting rules become slow and hard to maintain.
* **Uncertainty:** it expects clean true/false facts, so vague input like “kind of tired” is hard to handle.
* **No learning:** humans must hand-write every rule (the *knowledge acquisition bottleneck*).

## **2. Logic and Reasoning**

### **2.1 Why Logic Matters**

Symbolic AI represents knowledge as logical statements, and logic supplies the rules for reasoning from them. The deck covers two levels: **propositional logic** (whole statements) and **predicate logic** (statements about objects and their properties).

---

### **2.2 Propositional Logic**

#### **2.2.1 Propositions**

A **proposition** is a declarative sentence that is **either true or false, but not both**.

* Propositions: “The sky is blue.” / “It is raining.” / “2 + 2 = 4.”
* Not propositions: questions (“Is it raining?”) and commands (“Close the door”), because they have no truth value.

By convention, propositions are given letters such as **p** and **q**.

#### **2.2.2 Boolean Operators**

Operators combine propositions. Using the notes’ example, **p** = “It is raining” and **q** = “It is windy”:

| Operator | Symbol | Meaning | Example |
| ----- | ----- | ----- | ----- |
| AND | p ∧ q | True only if **both** are true | “It is raining and windy” |
| OR | p ∨ q | True if **at least one** is true | “It is raining or windy” |
| NOT | ¬p | Flips the truth value | “It is not raining” |

Truth table:

| p | q | p ∧ q | p ∨ q | ¬p |
| ----- | ----- | ----- | ----- | ----- |
| T | T | T | T | F |
| T | F | F | T | F |
| F | T | F | T | T |
| F | F | F | F | T |

#### **2.2.3 Logical Equivalences**

Two statements are **equivalent (≡)** if they have the same truth value in every situation.

* **De Morgan’s Laws**
  * ¬(p ∧ q) ≡ ¬p ∨ ¬q (“not both” means “at least one is not”)
  * ¬(p ∨ q) ≡ ¬p ∧ ¬q (“neither” means “both are not”)
* **Double Negation:** ¬(¬p) ≡ p

Example: “It is not true that it is raining **and** windy” is the same as “It is not raining **or** it is not windy.”

#### **2.2.4 Implication and Biconditional**

**Implication (p → q):** “if p, then q.” **p** is the *antecedent* (premise) and **q** is the *consequent* (conclusion).

* Example: “If it is raining, then the ground is wet.”
  * It is **false only when p is true and q is false** (raining but the ground is dry). In every other case it is true.
* **Biconditional (p ↔ q):** “p if and only if q.” p and q always have the **same truth value**.
  * Example: “You can access the system if and only if you have the correct password.”

| p | q | p → q | p ↔ q |
| ----- | ----- | ----- | ----- |
| T | T | T | T |
| T | F | **F** | F |
| F | T | T | F |
| F | F | T | T |

#### **2.2.5 Inference Rules**

**Inference rules** let us derive new conclusions from known statements.

| Rule | Latin meaning | Pattern | Example |
| ----- | ----- | ----- | ----- |
| **Modus Ponens** | “mode that affirms” | p → q, and p is true ⟹ **q** is true | “If it rains, the ground is wet.” It is raining, so the ground is wet. |
| **Modus Tollens** | “mode that denies” | p → q, and q is false ⟹ **p** is false | “If it rains, the ground is wet.” The ground is dry, so it is not raining. |

#### **2.2.6 Role in AI**

* **Knowledge representation:** facts become propositions, such as “the lights are on” or “the door is locked” in a smart home.
* **Logical inference:** from “if the traffic light is red, then stop” and “the traffic light is red,” a self-driving system infers “stop the vehicle.”

### **2.3 Predicate Logic**

#### **2.3.1 Why We Need It**

Propositional logic can’t say “all cats are mammals” in a general way. Predicate logic can, because it adds **variables, predicates, and quantifiers**.

#### **2.3.2 Predicates and Quantifiers**

* **Predicate:** a statement with variables that is true or false depending on their values. Example: **Even(x)** is true when x is an even number.
* **Universal quantifier (∀):** true for **all** elements in the domain.
  * ∀x (Cat(x) → Mammal(x)) means “every cat is a mammal.”
* **Existential quantifier (∃):** true for **at least one** element.
  * ∃x (Prime(x) ∧ x < 10) means “some prime number is less than 10.”

Memory aid: ∀ is an upside-down **A** (“for **A**ll”) and ∃ is a backwards **E** (“there **E**xists”).

#### **2.3.3 Translating English into Logic**

Four steps:

1. **Identify the predicates** (properties or relationships).
2. **Introduce variables** for the objects involved.
3. **Apply quantifiers** (all or at least one).
4. **Formulate the expression.**

Example: “Some birds can fly” becomes **∃y (Bird(y) ∧ CanFly(y))**, meaning there is at least one y that is a bird and can fly.

Tip: ∀ usually pairs with **→** and ∃ usually pairs with **∧**.

#### **2.3.4 Logical Connectives**

Predicate logic uses the same connectives (∧, ∨, →, ¬) to build complex statements:

* Even(x) ∧ Prime(x): x is even and prime
* Positive(x) ∨ Negative(x): x is positive or negative
* Adult(x) → CanVote(x): if x is an adult, x can vote
* ¬Married(x): x is not married
* ∀x (Even(x) → Positive(x)): every even number is positive

**Note:** the last example on your slide, ∀x(Even(x) → Positive(x)) ∧ Prime(x), has a scope problem. The ∧ Prime(x) sits outside the quantifier, so that x is unbound. Written correctly it would be ∀x((Even(x) → Positive(x)) ∧ Prime(x)), which is probably a deliberate “spot the error” example, but check with your instructor.

#### **2.3.5 Instantiation**

* **Universal Instantiation (UI):** from a statement about *all* x, conclude it for a *specific* element a.
  * ∀x(P(x) → Q(x)) ⟹ P(a) → Q(a)
  * “All humans are mortal” ⟹ “If Socrates is human, he is mortal.”
* **Existential Instantiation (EI):** from “something exists,” name a specific element c that satisfies it.
  * ∃x(P(x) ∧ Q(x)) ⟹ P(c) ∧ Q(c)
  * Here **c must be a new name** not already used. You know *something* satisfies it, but not which thing.

#### **2.3.6 Generalization**

* **Universal Generalization (UG):** P(a) → Q(a) ⟹ ∀x(P(x) → Q(x))
* **Existential Generalization (EG):** P(c) ∧ Q(c) ⟹ ∃x(P(x) ∧ Q(x))

**“Do you see anything strange for the above 4 rules?”** Here is the likely answer:

* **UI and EG are always safe.** Going from “all” to one, or from one to “there exists,” never loses truth.
* **UG is risky.** Showing something for *one* element doesn’t prove it for *all*. “3 is odd and prime” doesn’t mean everything is. UG is valid **only if a is arbitrary**, meaning you assumed nothing special about it.
* **EI is restricted.** The constant c must be fresh, because you only know *some* element works.

So the four rules are not symmetrical: two are unrestricted and two come with conditions.

#### **2.3.7 Applications**

* ∀n (Even(n)): every number is even (a false statement, but valid logic)
* ∃x (x ∈ S ∧ x > 10): the set S has an element greater than 10
* ∃x (Honest(x) ∧ Trustworthy(x)): someone is honest and trustworthy
* ∀o (Car(o) → HasFourWheels(o)): every car has four wheels

This shows a statement can be well-formed and still false. Logic tests structure, not truth in the real world.

#### **2.3.8 Rules of Inference in Predicate Logic (Slide 20)**

| Rule | Given | Conclude |
| ----- | ----- | ----- |
| **Universal Modus Ponens** | ∀x(P(x)→Q(x)) and P(a) | Q(a) |
| **Universal Modus Tollens** | ∀x(P(x)→Q(x)) and ¬Q(a) | ¬P(a) |
| **Existential Instantiation** | ∃xP(x) | P(c) for a specific c |
| **Existential Generalization** | P(c) for a specific c | ∃xP(x) |

Example of Universal Modus Ponens: “All humans are mortal” and “Socrates is human” give “Socrates is mortal.”

---

### **2.4 Propositional vs. Predicate Logic**

|  | Propositional | Predicate (First-Order) |
| ----- | ----- | ----- |
| Basic unit | Whole statements (p, q) | Predicates, variables, objects |
| Quantifiers | None | ∀ and ∃ |
| Expressiveness | Limited | Much richer |
| Can say “all cats are mammals”? | No | Yes |
| Complexity | Simpler, decidable | More powerful, harder to automate |

## **3. Knowledge Representation**

### **3.1 What It Is**

Knowledge representation is how an AI system stores knowledge **in a form it can reason with**. A computer doesn’t “just know” that a cat is an animal; someone must encode it.

A good representation is **expressive** (captures what matters), **inferable** (new facts can be derived), **efficient**, and **understandable** to humans.

### **3.2 The Five Approaches**

#### **3.2.1 Logic-Based Representation**

| Type | What it does | Example |
| ----- | ----- | ----- |
| **Propositional logic** | Simple true/false statements joined by AND, OR, NOT, IF-THEN | P = “It is raining”; ¬P = “It is not raining”; `Raining → GroundWet` |
| **First-Order Logic (FOL)** | Adds objects, predicates, variables and quantifiers (“for all”, “there exists”) | ∀x (Human(x) → Mortal(x)); with `Human(Socrates)`, the system concludes `Mortal(Socrates)` |

* **Strength:** precise and supports rigorous reasoning (basis of Prolog).
* **Limit:** propositional logic can’t talk about “all” or “some”; FOL is powerful but can be costly to compute.

#### **3.2.2 Semantic Networks**

A **graph**: nodes are concepts or entities, links are the relationships.

* *Animal network:* Cat/Bear/Whale **is a** Mammal → Mammal **is an** Animal; Mammal **has** Vertebra; Cat and Bear **have** Fur; Fish and Whale **live in** Water.
* *John Doe network:* John Doe **is** a Person, **lives in** Liverpool, **works in** London; both are Cities.
* **Inference by following links:** Cat → Mammal → Animal, so a cat is an animal with a vertebra.
* **Strength:** easy to visualize. **Limit:** the meaning of links can be vague.

#### **3.2.3 Frames and Scripts**

|  | Meaning | Example |
| ----- | ----- | ----- |
| **Frame** | A data structure for a stereotypical object or situation, with **slots** (properties) and values (and default values) | “Car” frame: make, model, year, color |
| **Script** | A **sequence of frames** describing a typical chain of events | “Going to a restaurant”: reservation → ordering → paying the bill |

Hearing “we went to a restaurant,” the system fills in defaults (a menu, a waiter, a bill) automatically.

#### **3.2.4 Rule-Based Representation**

Knowledge as **production rules** (IF-THEN) that capture conditions and actions and infer new knowledge.

* Example: *If the patient has fever and cough, then consider a respiratory infection.*
* (This approach leads directly into Section 4.)

#### **3.2.5 Ontologies**

Formal representations of the **concepts in a domain and their relationships**, giving a shared vocabulary and a hierarchical structure.

* Example: a medical ontology defines *disease*, *symptom*, *treatment*, and how they relate (Pneumonia is-a LungDisease is-a Disease).
* IoT example from the slides: Thing, Device, IoT Middleware, Variable, and so on, connected by “Is-a,” “HasProperty,” “contains,” “is a part of.”
* Modern descendants: knowledge graphs, the Semantic Web (OWL, RDF).

### **3.3 Quick Comparison**

| Approach | Best for | Main weakness |
| ----- | ----- | ----- |
| Propositional logic | Simple true/false facts | Can’t generalize |
| First-order logic | Precise, general reasoning | Computationally heavy |
| Semantic networks | Showing relationships visually | Vague link meaning |
| Frames/Scripts | Typical objects and situations | Rigid, struggles with exceptions |
| Rules | Decisions and actions | Hard to maintain at scale |
| Ontologies | Shared, consistent domain vocabulary | Costly to build |

### **3.4 Applications**

* **Medical diagnosis:** captures symptoms, diseases and expertise
* **Natural language understanding:** linguistic knowledge to understand and generate language
* **Robotics:** spatial reasoning, object manipulation, task planning
* **Expert systems:** domain knowledge for expert-level advice

### **3.5 Challenges**

* **Knowledge acquisition bottleneck:** extracting knowledge from experts is slow and expensive.
* **Common sense:** humans know countless obvious things that are hard to write down (the Cyc project has tried for decades).
* **Exceptions and uncertainty:** most birds fly, but penguins don’t, and pure logic handles this awkwardly.

## **4. Rule-Based Systems and Expert Systems**

### **4.1 Rule-Based Systems (Production Systems)**

AI systems that operate on a set of conditional **IF-THEN rules**. Each rule has:

* a **condition** (the “if” part)
* an **action** (the “then” part)

**Examples:**

* If temperature > 30°C → turn on the air conditioning.
* If customer purchases > $100 → offer a 10% discount.

#### **4.1.1 Components**

| Component | Role |
| ----- | ----- |
| **Knowledge Base** | Stores the rules |
| **Working Memory** | Holds the facts about the current case |
| **Inference Engine** | Matches facts to rules and fires them |

The Knowledge Base feeds the Inference Engine, which exchanges information in both directions with Working Memory.

#### **4.1.2 Worked Example: Smart Thermostat**

* Rule 1: If temperature > 25°C → air conditioning ON
* Rule 2: If temperature < 20°C → heating ON
* Fact: current temperature = 28°C → the engine matches Rule 1 → AC turns on.

#### **4.1.3 Worked Example: Car Diagnosis**

* Rule 1: IF engine won’t start AND lights are dim → battery is weak
* Rule 2: IF battery is weak → recommend charging or replacing it
* Facts: engine won’t start, lights dim → Rule 1 fires, adding “battery weak” to memory → Rule 2 fires → recommendation.

#### **4.1.4 How the Inference Engine Reasons**

| Method | Direction | Analogy |
| ----- | ----- | ----- |
| **Forward chaining** | Facts → conclusions (data-driven) | A detective collecting clues |
| **Backward chaining** | Hypothesis → supporting facts (goal-driven) | A doctor checking “could it be flu?” symptom by symptom |

**Conflict resolution:** when several rules can fire at once, the engine picks by priority, specificity or recency.

### **4.2 Expert Systems**

AI systems designed to **emulate the decision-making of a human expert** in one specific domain, giving expert-level advice on complex problems.

#### **4.2.1 Three Main Components**

| Component | Role |
| ----- | ----- |
| **Knowledge Base** | Domain facts, rules and heuristics |
| **Inference Engine** | Reasons over the knowledge base to reach conclusions |
| **User Interface** | Lets users enter data and receive recommendations |

#### **4.2.2 Architecture**

1. **Experts** pass their expertise (plus printed materials) to a **Knowledge Engineer**.
2. The Knowledge Engineer builds the **Knowledge Base** and provides the control structure for the **Inference Engine**.
3. The Inference Engine uses **Working Memory** and can connect through an **External Interface** to databases, spreadsheets and models.
4. Users communicate through the **User Interface** (questions and answers in, solutions out).

#### **4.2.3 Famous Examples**

| System | Era | What it did |
| ----- | ----- | ----- |
| **DENDRAL** | 1960s | Worked out organic molecule structures from mass spectrometer data; often called the first expert system |
| **MYCIN** | 1970s | Diagnosed bacterial blood infections and recommended antibiotics using ~600 rules and **certainty factors** (e.g. “organism is E. coli, certainty 0.7”); matched specialists in tests but was never used clinically |
| **XCON/R1** | 1980s | Configured computer orders for Digital Equipment Corporation, reportedly saving millions of dollars a year |

### **4.3 Rule-Based vs. Expert Systems**

|  | Rule-Based Systems | Expert Systems |
| ----- | ----- | ----- |
| **Focus** | Specific conditional rules for decisions or tasks | Emulating how a human expert decides in a domain |
| **Scope** | More general-purpose, wide range of applications | Highly specialized (medicine, finance, engineering) |
| **Extras** | Rules + inference engine | Adds knowledge engineering, user interface, often explanations |

**Simple way to remember:** every expert system is rule-based (or uses similar reasoning), but not every rule-based system is an expert system. A thermostat is rule-based; MYCIN is an expert system.

### **4.4 Strengths and Weaknesses of Rule-Based Systems and Expert Systems**

| Strengths | Weaknesses |
| ----- | ----- |
| Transparent and explainable | Expensive to build the knowledge base |
| Consistent, never tired | **Brittle**: fails outside its narrow domain |
| Preserves scarce expert knowledge | Cannot learn on its own |
| Works well in well-defined domains | Large rule sets are hard to maintain |

## **5. Planning and Problem Solving**

### **5.1 Overview**

**Planning** is the process of finding a sequence of actions that transforms a given **initial state** into a desired **goal state**. It reasons about actions, their effects, and the states of the world.

**Problem solving** is finding solutions to complex, often abstract problems with computational methods: searching for solutions, reasoning about possible actions, and evaluating the outcomes.

The two are closely related. Both explore a space of possible situations, but they differ in how much they look inside a state:

|  | General problem solving (search) | Automated planning |
| ----- | ----- | ----- |
| How a state is seen | A "black box": the algorithm can only test it, expand it, and compare it | A set of symbolic facts (for example `On(A,B)`, `Clear(A)`) the planner can inspect |
| How actions are described | A function that returns the next states | Preconditions and effects written in logic |
| Typical output | A path to a goal | A sequence of actions (a plan) that a human can read and verify |
| Typical examples | Puzzles, route finding, games | Robot tasks, logistics, spacecraft operations |

**Why this is symbolic AI.** The states, actions and goals are written down explicitly as symbols, so a plan can be explained step by step ("I picked up A because the goal needs A on B, and picking up is a precondition of stacking").

**Historical milestones**

| Year | Milestone |
| ----- | ----- |
| 1950 | Shannon proposes how a computer could play chess by searching ahead and scoring positions |
| 1956 | Logic Theorist uses heuristic search to find proofs |
| 1957 | General Problem Solver (GPS) introduces means-ends analysis |
| 1968 | A* search is published (Hart, Nilsson, Raphael) |
| 1971 | STRIPS, a planner with a simple action language (Fikes, Nilsson) |
| 1997 | Deep Blue defeats the world chess champion using game-tree search |

---

### **5.2 Formulating a Problem**

Before searching, a problem must be written in a form a program can use. A **well-defined problem** has five parts:

| Component | Meaning | Example: route finding |
| ----- | ----- | ----- |
| **Initial state** | Where the agent starts | In city A |
| **Actions** | What can be done in a state (with preconditions and effects) | Drive to any neighboring city |
| **Transition model** | The state that results from an action | Driving from A to B leads to "in city B" |
| **Goal test** | How to recognize success | Is the agent in city Z? |
| **Path cost** | A number measuring how good a path is | Total distance in km |

The **state space** is the set of all states reachable from the initial state by any sequence of actions. A **solution** is a path from the initial state to a goal state; an **optimal solution** is the one with the lowest path cost.

**Example problems**

| Problem | States | Actions | Goal test | Path cost |
| ----- | ----- | ----- | ----- | ----- |
| **8-puzzle** | Positions of 8 tiles and a blank on a 3x3 board (181,440 reachable arrangements) | Slide the blank up, down, left or right | Tiles are in the target order | 1 per move |
| **Route finding** | Cities on a map | Drive along a road | Reach the destination | Road distance |
| **Robot in a house** | Robot location plus which doors are open | Walk, open a door | Robot is in the garage | Number of steps |

**Key terms**

* **Node:** a state plus bookkeeping (parent node, action taken, path cost so far).
* **Frontier (open list):** nodes generated but not yet expanded.
* **Explored set (closed list):** states already expanded, kept so the search does not loop.
* **Branching factor (b):** the number of actions available per state.
* **Depth (d):** the number of steps to the shallowest goal. **Maximum depth (m):** the longest path in the space.
* **Expanding a node:** generating all its children.

#### **One algorithm, many strategies**

Every search method below fits the same skeleton. Only the order in which the frontier is processed changes.

```
frontier = [initial state]
explored = {}
repeat:
    if frontier is empty: return FAILURE
    node = remove one node from frontier      # the strategy decides which
    if goal_test(node): return path to node
    add node.state to explored
    for each action applicable in node.state:
        child = result of the action
        if child.state not in explored and not already in frontier:
            add child to frontier
```

| Frontier is a... | Strategy |
| ----- | ----- |
| Queue (first in, first out) | Breadth-first search |
| Stack (last in, first out) | Depth-first search |
| Priority queue ordered by path cost g(n) | Uniform-cost search |
| Priority queue ordered by heuristic h(n) | Greedy best-first search |
| Priority queue ordered by g(n) + h(n) | A* search |

### **5.3 Evaluating Search Strategies and Combinatorial Explosion**

Four criteria are used to compare strategies:

| Criterion | Question |
| ----- | ----- |
| **Completeness** | If a solution exists, is the algorithm guaranteed to find it? |
| **Optimality** | Does it find the lowest-cost solution? |
| **Time complexity** | How many nodes are generated? |
| **Space complexity** | How many nodes must be held in memory? |

**Combinatorial explosion.** With branching factor b and solution depth d, a search may have to look at about b^d nodes. Take b = 10 and a computer that checks one million nodes per second:

| Depth d | Nodes (about 10^d) | Time at 10^6 nodes/s |
| ----- | ----- | ----- |
| 2 | 100 | instant |
| 4 | 10,000 | 0.01 s |
| 6 | 1,000,000 | 1 s |
| 8 | 100,000,000 | about 100 s |
| 10 | 10,000,000,000 | about 2.8 hours |
| 12 | 1,000,000,000,000 | about 11.6 days |

Two extra steps of depth multiply the work by 100. Real problems are far worse: chess has a branching factor of about 35, and Shannon (1950) estimated roughly 10^120 possible games. This is why early symbolic systems that worked on small puzzles failed to scale, and why **heuristics** and **domain knowledge** became central.

### **5.4 Uninformed (Blind) Search**

**Uninformed search** algorithms use no knowledge about the goal or the structure of the space beyond the problem definition. They explore systematically until the goal is found.

#### **Breadth-First Search (BFS)**

Expands the shallowest unexpanded node first, so it explores all neighbors at the current depth before going one level deeper. Uses a **queue**.

* Complete (if b is finite). Optimal when every step costs the same.
* Time and space: O(b^d). Memory is its main weakness.

#### **Depth-First Search (DFS)**

Expands the deepest unexpanded node first, going as far as possible along one branch before backtracking. Uses a **stack** (or recursion).

* Space is small: O(b·m).
* Not optimal. Not complete in infinite or looping spaces unless repeated states are checked.
* Time: O(b^m), which is bad if m is much larger than d.

#### **Uniform-Cost Search (UCS)**

Expands the node with the lowest path cost g(n) so far. It is BFS generalized to steps of different cost.

* Complete and optimal when every step cost is greater than zero.
* It can explore a very large number of cheap but useless nodes because it has no sense of direction.

#### **Depth-Limited and Iterative Deepening Search**

* **Depth-limited search** is DFS with a cutoff depth l, which avoids endless descent.
* **Iterative deepening** runs depth-limited search with l = 0, 1, 2, ... until a goal is found. It combines BFS's completeness and optimality (for unit step costs) with DFS's small memory: time O(b^d), space O(b·d). The repeated work at shallow levels is small because most nodes sit at the deepest level.

#### **Worked example: BFS versus DFS**

A small tree: A is the start; A has children B and C; B has children D and E; C has child F. The goal is F. Neighbors are visited left to right.

| Strategy | Order of expansion | Result |
| ----- | ----- | ----- |
| BFS | A, B, C, D, E, F | Visits every shallower node (levels 0 and 1, then level 2) before reaching F at depth 2 |
| DFS | A, B, D, E, C, F | Also reaches F, but only after exploring the whole left branch |

#### **Comparison**

| Algorithm | Complete? | Optimal? | Time | Space |
| ----- | ----- | ----- | ----- | ----- |
| BFS | Yes | Yes, if step costs are equal | O(b^d) | O(b^d) |
| DFS | No (in infinite or cyclic spaces) | No | O(b^m) | O(b·m) |
| Uniform-cost | Yes | Yes | About O(b^(1+C*/ε)) | Same as time |
| Depth-limited | No (if the goal is deeper than l) | No | O(b^l) | O(b·l) |
| Iterative deepening | Yes | Yes, if step costs are equal | O(b^d) | O(b·d) |

(C* is the optimal solution cost and ε the smallest step cost.)

---

### **5.5 Informed (Heuristic) Search**

**Informed search** uses **domain-specific knowledge** to decide which node looks most promising, so far fewer nodes are expanded.

A **heuristic function h(n)** estimates the cost of the cheapest path from node n to a goal. It is a rule of thumb, not a guarantee.

**Examples of heuristics**

| Problem | Heuristic h(n) |
| ----- | ----- |
| Route finding | Straight-line distance to the destination |
| 8-puzzle (h1) | Number of tiles out of place |
| 8-puzzle (h2) | Sum of the Manhattan distances of each tile from its target square |

**Two properties matter**

* **Admissible:** h(n) never overestimates the true remaining cost. Straight-line distance is admissible because no road is shorter than the straight line.
* **Consistent:** for every step from n to n' with cost c, h(n) ≤ c + h(n'). Consistency implies admissibility.

In the 8-puzzle, h2 (Manhattan distance) is always at least as large as h1 (misplaced tiles) while staying admissible, so h2 expands fewer nodes. We say h2 **dominates** h1.

**Designing heuristics: relaxed problems.** A good admissible heuristic is the exact cost of a *simpler* version of the problem with some rules removed. If the 8-puzzle rule "a tile moves only into the adjacent blank" is relaxed to "a tile moves to any adjacent square," the exact solution cost of the relaxed problem is the Manhattan distance.

#### **Greedy Best-First Search**

Expands the node that looks closest to the goal: it orders the frontier by **f(n) = h(n)** only.

* Often fast because it heads straight for the goal.
* Not optimal and not complete (it can be misled into a dead end), because it ignores the cost already paid.

#### **A\* Search**

Orders the frontier by

**f(n) = g(n) + h(n)**

where g(n) is the cost paid so far and h(n) the estimated cost still to go. So f(n) is the estimated cost of the cheapest solution *through* n.

* **Optimal** when h is admissible (tree search) or consistent (graph search).
* Complete when step costs are above zero.
* Weakness: it keeps all generated nodes in memory, which can be exhausted on large problems. IDA* (iterative-deepening A*) trades time for memory.

#### **Worked example: A\* on a small graph**

Edge costs: S→A = 1, S→B = 4, A→B = 2, A→G = 6, B→G = 3. Goal: G. Heuristic: h(S) = 5, h(A) = 4, h(B) = 3, h(G) = 0 (admissible and consistent).

| Step | Node expanded | Frontier after expansion, as node (g + h = f) |
| ----- | ----- | ----- |
| 1 | S | A (1+4=5), B (4+3=7) |
| 2 | A | B via A (3+3=6, replaces 7), G via A (7+0=7) |
| 3 | B (cost 3) | G via B (6+0=6, replaces 7) |
| 4 | G | Goal reached |

Solution: **S → A → B → G with cost 6**, which is optimal (the alternatives cost 7). Note that the direct-looking route S → B → G (cost 7) and S → A → G (cost 7) were both worse.

#### **Comparison**

| Algorithm | Uses | Complete? | Optimal? | Main strength | Main weakness |
| ----- | ----- | ----- | ----- | ----- | ----- |
| Uniform-cost | g(n) | Yes | Yes | Guaranteed cheapest path | No sense of direction |
| Greedy best-first | h(n) | No | No | Very fast when h is good | Can be misled |
| A* | g(n) + h(n) | Yes | Yes (admissible h) | Optimal and focused | High memory use |

### **5.6 Adversarial Search (Game Playing)**

**Adversarial search** applies when an agent's actions are opposed by another agent. The classic setting is a two-player, **zero-sum**, **perfect-information**, turn-taking game such as chess, checkers or tic-tac-toe: one player's gain is exactly the other's loss, and both see the whole board.

A game is defined by: the initial state, which player moves, the legal actions, the result of an action, a **terminal test** (is the game over?), and a **utility** (the final score, for example +1 win, 0 draw, -1 loss).

#### **Minimax Algorithm**

Two players are named **MAX** (tries to maximize the score) and **MIN** (tries to minimize it). The algorithm builds the game tree, assigns utilities to terminal states, and passes values upward: a MAX node takes the **largest** child value and a MIN node takes the **smallest**. It assumes the opponent always plays its best move, so it minimizes the possible loss in the worst case.

**Worked example.** MAX is to move and has three moves, after each of which MIN chooses among three replies. The leaf scores are:

| MAX's move | MIN's replies (leaf scores) | MIN picks | Value |
| ----- | ----- | ----- | ----- |
| A | 3, 12, 8 | minimum | 3 |
| B | 2, 4, 6 | minimum | 2 |
| C | 14, 5, 2 | minimum | 2 |

MAX picks the maximum of (3, 2, 2) = **3**, so MAX plays move A.

* Complete for finite trees; optimal against a perfect opponent.
* Time O(b^m), space O(b·m) (depth-first).

#### **Alpha-Beta Pruning**

An optimization of minimax that returns **exactly the same decision** while skipping branches that cannot affect it. It tracks two bounds along the current path:

* **α (alpha):** the best value MAX can already guarantee.
* **β (beta):** the best value MIN can already guarantee.

A branch is cut as soon as α ≥ β.

**Continuing the example.** After move A, MAX is guaranteed at least 3 (α = 3). In move B, MIN's first reply scores 2, so MIN can hold B to at most 2, which is below 3. The remaining leaves (4 and 6) cannot change MAX's choice and are **pruned**. Move C is examined fully, because its 2 comes last. Result: 7 of the 9 leaves are evaluated and the answer is still 3.

* Worst case (bad move ordering): no savings, O(b^m).
* Best case (best moves examined first): O(b^(m/2)), so it can search about **twice as deep** in the same time.

#### **Making game search practical**

| Technique | Purpose |
| ----- | ----- |
| **Depth limit + evaluation function** | Stop at a fixed depth and score the position with a heuristic (for chess, material count and piece positions) |
| **Move ordering** | Try promising moves first so more branches are pruned |
| **Iterative deepening** | Search deeper until time runs out, always keeping the best move found so far |
| **Transposition tables** | Remember positions already evaluated, since different move orders reach the same position |

Deep Blue, which beat world champion Garry Kasparov in 1997, is the best-known example of this kind of search: deep alpha-beta search, special-purpose hardware, and a hand-built evaluation function. Newer game systems, such as those for Go, combine search with learned evaluation, a point where symbolic search meets machine learning.

### **5.7 Local Search and Optimization**

**Local search** is used when only the **final state** matters, not the path to it (placing 8 queens so none attack each other, timetabling, circuit layout). It keeps a **single current solution** and repeatedly moves to a neighboring solution, hoping to reach an optimal one. It uses very little memory and can handle huge spaces, but it is not systematic and gives no guarantee.

A useful picture is the **state-space landscape**: each state has a height given by an objective function, and the goal is the highest peak (or lowest valley).

| Landscape feature | Meaning | Problem for the search |
| ----- | ----- | ----- |
| Global maximum | The best state anywhere | The target |
| Local maximum | Better than all neighbors but not the best overall | The search gets stuck |
| Plateau | A flat area | No direction to move |
| Ridge | A narrow slope that rises sideways | Single steps do not climb it |

#### **Hill Climbing**

```
current = initial solution
loop:
    neighbor = best-valued neighbor of current
    if value(neighbor) <= value(current): return current
    current = neighbor
```

It always moves uphill and stops when no neighbor is better. It is simple and fast, but it halts at local maxima, ridges and plateaus. For 8-queens, steepest-ascent hill climbing started from a random board gets stuck most of the time (Russell and Norvig report about 86% of runs). Common fixes: **random-restart hill climbing** (run many times from random starts), sideways moves, and stochastic variants.

#### **Simulated Annealing**

Inspired by annealing in metallurgy, where a metal is heated and cooled slowly so it settles into a low-energy state. The algorithm picks a *random* neighbor:

* If the move **improves** the solution, always accept it.
* If the move is **worse** by an amount Δ, accept it with probability e^(−Δ/T), where **T** is a "temperature" that is lowered over time.

| Temperature | Behavior |
| ----- | ----- |
| High T | Accepts many bad moves, so it explores widely and can escape local maxima |
| Low T | Rarely accepts bad moves, so it behaves like hill climbing and settles |

If T is lowered slowly enough, simulated annealing can find the global optimum with probability approaching 1, but a slow schedule costs time (Kirkpatrick et al., 1983). It gives only an **approximate** solution in practice.

| | Hill climbing | Simulated annealing |
| ----- | ----- | ----- |
| Accepts worse moves? | Never | Sometimes, with probability that falls as T falls |
| Gets stuck at local maxima? | Yes | Much less likely |
| Cost | Cheap | Needs a tuned cooling schedule |

### **5.8 Automated Planning**

Search treats states as opaque. **Planning** gives states and actions an explicit logical structure, so the planner can reason about *why* an action is useful and prune irrelevant ones.

#### **Classical planning assumptions**

| Assumption | Meaning |
| ----- | ----- |
| Deterministic | Each action has exactly one outcome |
| Fully observable | The agent knows the complete current state |
| Static | Nothing changes unless the agent acts |
| Discrete | States and time come in steps |
| Single agent | No other actors |

Real situations often break these assumptions, which leads to extensions (contingent planning, probabilistic planning, temporal planning, replanning).

#### **The STRIPS representation**

STRIPS (Fikes and Nilsson, 1971) describes the world as a **set of true facts** (ground atoms). Anything not listed is assumed false (the **closed-world assumption**). Each **action** has:

| Part | Meaning |
| ----- | ----- |
| **Preconditions** | Facts that must hold for the action to be applicable |
| **Delete list** | Facts that become false |
| **Add list** | Facts that become true |

The new state is: **(old state − delete list) ∪ add list**. Everything not mentioned stays as it was. This convention is STRIPS's practical answer to the frame problem (below).

#### **Worked example: a tiny blocks world**

Actions:

| Action | Preconditions | Delete | Add |
| ----- | ----- | ----- | ----- |
| `Pickup(x)` | `Clear(x)`, `OnTable(x)`, `HandEmpty` | `OnTable(x)`, `Clear(x)`, `HandEmpty` | `Holding(x)` |
| `Stack(x,y)` | `Holding(x)`, `Clear(y)` | `Holding(x)`, `Clear(y)` | `On(x,y)`, `Clear(x)`, `HandEmpty` |

* **Initial state:** `OnTable(A)`, `OnTable(B)`, `Clear(A)`, `Clear(B)`, `HandEmpty`
* **Goal:** `On(A,B)`

| Step | Action | Why it is applicable | State afterwards |
| ----- | ----- | ----- | ----- |
| 1 | `Pickup(A)` | A is clear, on the table, and the hand is empty | `OnTable(B)`, `Clear(B)`, `Holding(A)` |
| 2 | `Stack(A,B)` | The hand holds A and B is clear | `OnTable(B)`, `On(A,B)`, `Clear(A)`, `HandEmpty` |

The goal `On(A,B)` now holds. The **plan** is `[Pickup(A), Stack(A,B)]`.

#### **Planning strategies**

| Strategy | Idea |
| ----- | ----- |
| **Forward (progression) search** | Start at the initial state and apply applicable actions toward the goal |
| **Backward (regression) search** | Start from the goal and find actions that could produce it, replacing the goal with their preconditions |
| **Means-ends analysis (GPS, STRIPS)** | Compare the current state with the goal, find the *difference*, choose an action that reduces it, and make its preconditions new subgoals |
| **Partial-order planning** | Order actions only where necessary ("least commitment") instead of fixing a full sequence early |
| **Planning graphs (GraphPlan)** | Build a compact layered structure of what could be true at each step and extract a plan from it |
| **Heuristic planners** | Derive a heuristic automatically, often by *relaxing* the problem (for example, ignoring delete lists), and run A*-style search |
| **Hierarchical task networks (HTN)** | Break high-level tasks into subtasks using expert-written methods |

**Means-ends example.** Start: robot in the kitchen. Goal: robot in the garage.

1. Difference: location (kitchen versus garage).
2. An action that reduces it: `Walk(x, garage)`, with precondition "robot is at a place next to the garage" (the hallway).
3. The robot is not in the hallway, so "be in the hallway" becomes a subgoal.
4. `Walk(kitchen, hallway)` is applicable now.
5. Plan: `Walk(kitchen, hallway)`, then `Walk(hallway, garage)`.

#### **PDDL: a standard planning language**

The **Planning Domain Definition Language (PDDL)** is the common language for describing planning problems, used in the International Planning Competition. The `Stack` action above would look like:

```
(:action stack
  :parameters (?x ?y)
  :precondition (and (holding ?x) (clear ?y))
  :effect (and (not (holding ?x)) (not (clear ?y))
               (on ?x ?y) (clear ?x) (handempty)))
```

#### **Hard problems in planning**

| Problem | What it is |
| ----- | ----- |
| **Frame problem** | Stating what does *not* change when an action occurs. Writing it all out explicitly is impractical (McCarthy and Hayes, 1969) |
| **Qualification problem** | Listing every condition that must hold for an action to work ("start the car" assumes fuel, battery, no potato in the exhaust...) |
| **Ramification problem** | Capturing indirect effects of actions (moving a box also moves what is on it) |
| **Computational complexity** | Deciding whether a plan exists for even propositional STRIPS is PSPACE-complete (Bylander, 1994) |

#### **Execution and monitoring**

A plan is only as good as its model of the world. Real systems **monitor** execution, compare sensor readings with the expected state, and **replan** when they differ. This is where the brittleness of purely symbolic systems shows: if a fact is wrong (a blocked aisle labeled clear), a logically valid plan can still fail.

---

### **5.9 Constraint Satisfaction (extension)**

A **constraint satisfaction problem (CSP)** is a special kind of problem solving where states have an internal structure: a set of **variables**, a **domain** of values for each, and **constraints** that restrict combinations.

**Example: map colouring.** Variables: the regions of a map. Domain: {red, green, blue}. Constraint: neighboring regions must have different colors. A solution assigns a color to every region without breaking a constraint.

Solving methods:

* **Backtracking search:** assign variables one at a time and undo (backtrack) when a constraint is violated.
* **Constraint propagation** (for example forward checking, arc consistency): remove values that can no longer work, which detects dead ends early.
* **Heuristics:** choose the most constrained variable first.

CSPs fit scheduling, timetabling, configuration and resource allocation, the same kinds of tasks as early configuration expert systems.

| Area | How planning and search are used |
| ----- | ----- |
| **Route navigation** | Shortest-path search (A*-style algorithms) over road networks |
| **Game playing** | Minimax and alpha-beta search with evaluation functions (chess, checkers) |
| **Robotics** | Task planning: sequencing grasping, moving, and tool use |
| **Logistics and scheduling** | Delivery routes, factory schedules, timetables (often as CSPs or heuristic planning) |
| **Space missions** | The Remote Agent experiment on the Deep Space 1 spacecraft (1999) planned and monitored operations on board |
| **Theorem proving** | Heuristic search for proofs (Logic Theorist) |
| **Puzzles and games AI** | A* pathfinding for characters in video games |

Production rules (Section 4) can drive the choice of the next action, and the same forward and backward reasoning directions reappear as forward and backward planning.

### **5.11 Strengths and Limitations**

| Strengths | Limitations |
| ----- | ----- |
| Plans and decisions are explicit and can be explained | **Combinatorial explosion** makes large spaces intractable |
| Optimal solutions are guaranteed for suitable algorithms (A* with an admissible heuristic) | A good heuristic needs domain knowledge and design effort |
| Works without training data | A detailed, accurate model of the world must be written by hand (knowledge acquisition bottleneck) |
| Plans can be verified before execution | The frame, qualification and ramification problems |
| Same framework fits many domains | Struggles with uncertainty, partial observability and changing worlds |

**Challenges to remember**

* **Scalability:** time and memory grow exponentially with depth.
* **Heuristic quality:** a poor heuristic gives little help; an inadmissible one can lose optimality.
* **Modeling effort:** the action model is only as good as its author.
* **Open worlds:** real environments contain surprises the model never listed.

### **5.12 Summary: Choosing an Algorithm**

| Situation | Suitable approach |
| ----- | ----- |
| Unit step costs, small space, need shortest path | BFS |
| Memory is tight, many solutions | DFS or iterative deepening |
| Steps have different costs, no heuristic available | Uniform-cost search |
| Good heuristic available, optimal path needed | A* |
| Speed matters more than optimality | Greedy best-first |
| Two-player game | Minimax with alpha-beta pruning |
| Only the final state matters, space is huge | Hill climbing (with restarts) or simulated annealing |
| Actions have preconditions and effects, need an explainable plan | STRIPS/PDDL planner |
| Assigning values under constraints | CSP solver |

### **5.13 Hands-on: A\* in Python (optional)**

This reproduces the worked example in 5.5. It should print the cost 6 and the path S, A, B, G.

```python
import heapq

graph = {
    "S": {"A": 1, "B": 4},
    "A": {"B": 2, "G": 6},
    "B": {"G": 3},
    "G": {},
}
h = {"S": 5, "A": 4, "B": 3, "G": 0}      # heuristic estimates

def a_star(start, goal):
    frontier = [(h[start], 0, start, [start])]   # (f, g, state, path)
    best_g = {start: 0}
    while frontier:
        f, g, state, path = heapq.heappop(frontier)
        if state == goal:
            return g, path
        for nxt, cost in graph[state].items():
            new_g = g + cost
            if new_g < best_g.get(nxt, float("inf")):
                best_g[nxt] = new_g
                heapq.heappush(frontier,
                               (new_g + h[nxt], new_g, nxt, path + [nxt]))
    return None

print(a_star("S", "G"))    # (6, ['S', 'A', 'B', 'G'])
```

Try changing h("A") to 10 (an overestimate, so no longer admissible) and see whether the answer stays optimal.

## **6. Natural Language Processing (NLP) in Symbolic AI**

### **6.1 Overview**

**Natural language processing (NLP)** is the field of AI concerned with the interaction between computers and human language: enabling computers to **understand, interpret, and generate** language in a meaningful way.

**Symbolic NLP** (also called rule-based or knowledge-based NLP) does this with **formal rules, logic, and symbolic representations** that people write down, instead of patterns learned statistically from large text collections.

| | Symbolic NLP | Statistical / neural NLP |
| ----- | ----- | ----- |
| Source of language knowledge | Grammars, rules, dictionaries and ontologies written by linguists and engineers | Patterns learned from data |
| How it works | Match and apply rules; logical inference | Compute probabilities with learned models |
| Explainability | High: each decision traces to a rule | Low: decisions come from numerical weights |
| Needs training data | No (but needs expert effort) | Yes, often large amounts |
| Handles messy real text | Poorly | Well |
| Typical failure | Input not covered by any rule | Plausible but unfounded output |

#### **A typical processing pipeline**

| Stage | What happens | Example for "The cat chased the mouse." |
| ----- | ----- | ----- |
| 1. Tokenization | Split text into words and punctuation | The / cat / chased / the / mouse / . |
| 2. Morphological analysis | Find word structure and base forms | chased = chase + past tense |
| 3. Part-of-speech tagging | Label each word's grammatical category | The (determiner), cat (noun), chased (verb), the (determiner), mouse (noun) |
| 4. Syntactic parsing | Build the sentence structure | Subject "the cat", verb "chased", object "the mouse" |
| 5. Semantic interpretation | Build a representation of the meaning | `Chase(cat, mouse)` |
| 6. Discourse and pragmatics | Use context and intent | Who is "it" in the next sentence? Why was this said? |

Each stage hands symbolic structures to the next, and each stage can be implemented with rules.

---

### **6.2 Levels of Linguistic Analysis**

| Level | Question it answers | Example |
| ----- | ----- | ----- |
| **Lexical / morphological** | What are the words and their forms? | "unhappiness" = un + happy + ness |
| **Syntactic** | How are words arranged into valid structures? | "The cat chased the mouse" is grammatical; "Cat the mouse chased the" is not |
| **Semantic** | What does the sentence mean? | Who did what to whom |
| **Pragmatic / discourse** | What is meant in this context? | "Can you pass the salt?" is a request, not a question about ability |

Symbolic NLP has been strongest at the syntactic level and in narrow semantic domains, and weakest at pragmatics.

---

### **6.3 Syntax: Formal Grammars and Parsing**

**Syntax** is the structure of language: the arrangement of words, phrases and clauses into grammatically correct sentences.

#### **Formal grammars**

A **formal grammar** is a set of rules that generates the valid sentences of a language and captures their **hierarchical structure**. A **context-free grammar (CFG)** has rules with a single symbol on the left. The slide example, "The cat chased the mouse," can be generated by:

```
S   -> NP VP          (a sentence is a noun phrase followed by a verb phrase)
NP  -> Det N          (a noun phrase is a determiner followed by a noun)
VP  -> V NP           (a verb phrase is a verb followed by a noun phrase)
Det -> the
N   -> cat | mouse
V   -> chased
```

The resulting **parse tree**, in bracket notation:

```
(S (NP (Det the) (N cat))
   (VP (V chased)
       (NP (Det the) (N mouse))))
```

Reading it off: subject = "the cat", verb = "chased", object = "the mouse". These roles are what the next stage uses to understand who did what.

Other grammar families used in symbolic NLP include **phrase structure grammars**, **dependency grammars** (which link each word to its head word), and unification-based grammars that add features such as number and tense (so "the cats chases" is rejected).

#### **The Chomsky hierarchy**

Chomsky (1956) classified formal grammars by power:

| Type | Name | Recognized by | Use in NLP |
| ----- | ----- | ----- | ----- |
| 3 | Regular | Finite automata | Tokenizing, simple patterns, morphology |
| 2 | Context-free | Pushdown automata | Core of most syntactic parsing |
| 1 | Context-sensitive | Linear-bounded automata | Rarely used directly |
| 0 | Unrestricted | Turing machines | Theoretical |

Natural languages are generally thought to need slightly more than context-free power, but CFGs are the standard workhorse.

#### **Parsing**

**Parsing** is finding a parse tree for a sentence according to a grammar.

| Approach | Idea |
| ----- | ----- |
| **Top-down** | Start from S and expand rules until the words are matched |
| **Bottom-up** | Start from the words and combine them into larger phrases until S is reached |
| **Chart parsing (for example CYK, Earley)** | Store partial results in a table so the same sub-phrase is never re-parsed; worst-case time is cubic in sentence length |

#### **Ambiguity**

A sentence can have several valid parses, and a grammar alone cannot choose.

| Sentence | Two readings |
| ----- | ----- |
| "I saw the man with the telescope." | I used a telescope to see him, or the man had a telescope |
| "Flying planes can be dangerous." | Piloting planes is dangerous, or planes that are flying are dangerous |
| "The chicken is ready to eat." | The chicken will eat, or someone will eat the chicken |

Ambiguity is a central reason rule-based NLP is hard: the number of parses can grow quickly, and choosing the right one needs meaning and world knowledge.

---

### **6.4 Semantics: Representing Meaning**

**Semantics** is the meaning conveyed by words, phrases and sentences in context. In symbolic NLP, meaning is stored in a **semantic representation** drawn from the same toolkit as Section 3: formal logic, semantic networks, frames and ontologies.

#### **Logical forms**

| Sentence | Logical form |
| ----- | ----- |
| "The cat chased the mouse." | `Chased(cat1, mouse1)` |
| "Every cat chased a mouse." | `∀x (Cat(x) → ∃y (Mouse(y) ∧ Chased(x, y)))` |
| "Some bird can fly." | `∃y (Bird(y) ∧ CanFly(y))` |

The second sentence is **scope-ambiguous**: it can also mean there is *one particular mouse* that every cat chased, `∃y (Mouse(y) ∧ ∀x (Cat(x) → Chased(x, y)))`. Logic makes this ambiguity explicit.

#### **Meaning of the sentence in a semantic network**

For "The cat chased the mouse," a semantic network would hold nodes for *cat*, *chasing* and *mouse*, with labeled links such as **agent** (cat → chasing) and **patient** (mouse → chasing). The roles *agent* (who acts) and *patient* (who is acted upon) are called **semantic roles**.

#### **Lexical semantics: word meaning**

A single word can have several meanings (**word sense ambiguity**): "bank" can be a riverbank or a financial institution. Symbolic resources record word senses and relations. **WordNet** (Miller, 1995) groups words into sets of synonyms (*synsets*) linked by relations:

| Relation | Example |
| ----- | ----- |
| Synonymy | *car* ~ *automobile* |
| Hypernym (is-a, more general) | *cat* → *feline* → *carnivore* → *mammal* |
| Hyponym (more specific) | *mammal* → *cat* |
| Meronym (part-of) | *wheel* is part of *car* |

**Word sense disambiguation by rules** uses context clues: if "bank" appears near "river" or "fishing," choose the riverbank sense; if near "loan" or "account," choose the financial sense.

#### **Compositional semantics**

The meaning of a sentence is built from the meanings of its parts following the parse structure. Each grammar rule is paired with a rule for combining meanings, so the parse tree drives the construction of the logical form.

---

### **6.5 Knowledge Representation in Symbolic NLP**

Knowledge representation here means the **formal encoding and manipulation of knowledge about language and about the world**, including facts, rules and relationships (see Section 3).

| Resource | What it stores | Role in NLP |
| ----- | ----- | ----- |
| **Lexicon / dictionary** | Words with part of speech, forms, features | Tokenizing, tagging, parsing |
| **Grammar** | Syntactic rules | Parsing and generation |
| **Ontology** | Domain concepts and relations (disease, symptom, treatment) | Fixes the meaning of domain terms |
| **Semantic network / WordNet** | Word senses and relations | Disambiguation and similarity |
| **Logic-based representations** | Predicates, rules, facts | Reasoning about what a text says |
| **Knowledge graph** | Entities and labeled relations | Question answering, information retrieval |

### **6.6 Rule-Based NLP Tasks**

Rule-based systems use **explicitly defined rules and patterns** to analyze language. Typical tasks are part-of-speech tagging, syntactic parsing and information extraction.

#### **Part-of-speech (POS) tagging**

Assign each word a category (noun, verb, adjective...). Rule examples:

| Rule | Example | Weakness |
| ----- | ----- | ----- |
| A word ending in "-ing" is probably a verb | "running" | "ceiling" is a noun |
| "the", "a", "an" are determiners | "the" | None, a closed class |
| A capitalized word in mid-sentence is probably a proper noun | "London" | Fails on text in all capitals |
| A word after a determiner is probably a noun or adjective | "the quick" | "the run" (noun) vs "to run" (verb) |
| A word following "to" is probably a verb | "to swim" | "to London" |

**Worked example:** "The quick brown fox jumps over the lazy dog."

| Word | Rule applied | Tag |
| ----- | ----- | ----- |
| The | closed-class dictionary | Determiner |
| quick, brown | between determiner and noun, dictionary entry | Adjective |
| fox | follows adjectives, dictionary entry | Noun |
| jumps | after noun subject, ends in -s, dictionary entry | Verb |
| over | closed-class dictionary | Preposition |
| the | closed-class dictionary | Determiner |
| lazy | between determiner and noun | Adjective |
| dog | follows adjective | Noun |

Parsing then finds the subject ("the quick brown fox"), the verb ("jumps") and the prepositional phrase ("over the lazy dog"). A well-known rule-based tagger, Brill's (1992), began with simple tagging and applied a list of correction rules. Its rules were learned from data, so it is a hybrid case.

#### **Information extraction (IE)**

Information extraction identifies **specific entities and relationships** in unstructured text using predefined patterns.

| Target | Pattern idea | Example |
| ----- | ----- | ----- |
| Dates | Day/month/number formats, month names | `\d{1,2}/\d{1,2}/\d{4}`, "5 March 2026" |
| Person names | A capitalized word after a title such as "Dr." or "Mr." | "Dr. Chen" |
| Organizations | Capitalized words ending in "Inc.", "Ltd.", "University" | "Acme Ltd." |
| Money | Currency sign plus a number | "$250" |
| Relations | Textual patterns like "X such as Y" (Hearst patterns), "X, the CEO of Y" | "animals such as cats" implies *cat is-a animal* |

Systems also use **gazetteers** (lists of known names, places and organizations) alongside the patterns. Modern toolkits, for example spaCy's rule-based matcher, still offer this style of pattern writing.

### **6.7 Logic and Inference in Symbolic NLP**

Logic lets a system **reason about what a text says** and derive new knowledge from it. Information is stored as predicates and rules, in the style of Section 2 and the logic programming language Prolog.

**Worked example: a family knowledge base** (the slide example with "parent", "sibling", and "spouse")

Facts extracted from text:

```
parent(alice, bob).
parent(alice, carol).
parent(bob, dave).
spouse(bob, erin).
```

Rules:

```
sibling(X, Y)     :- parent(Z, X), parent(Z, Y), X \= Y.
grandparent(X, Z) :- parent(X, Y), parent(Y, Z).
```

Queries and results:

| Query | Result | Reasoning |
| ----- | ----- | ----- |
| `sibling(bob, carol)` | true | Alice is parent of both and they are different people |
| `grandparent(alice, W)` | W = dave | parent(alice, bob) and parent(bob, dave) |
| `spouse(bob, W)` | W = erin | Direct fact |

The system answers questions whose answers were **never stated**, such as "Is Alice Dave's grandparent?" It derived them. Such inference is the advantage of symbolic representation over simple keyword lookup. The facts themselves must still be extracted from text correctly (Section 6.6), and a wrong fact gives a valid-looking but wrong conclusion.

### **6.8 Sentiment Analysis**

**Sentiment analysis** discerns the emotional tone or polarity (positive, negative, neutral) of text such as reviews, social media posts and customer feedback.

A **rule-based** approach uses a **sentiment lexicon** (a list of words with polarity scores) plus rules for context.

| Word list example | Polarity |
| ----- | ----- |
| good, excellent, happy | Positive |
| bad, poor, disappointed | Negative |

Typical rules:

| Rule | Example | Effect |
| ----- | ----- | ----- |
| **Negation** flips polarity | "not good" | Positive becomes negative |
| **Intensifiers** increase strength | "very good" | Score × 1.5 |
| **Diminishers** reduce strength | "slightly bad" | Score × 0.5 |
| **Contrast words** shift emphasis to the second clause | "The food was great, but the service was awful" | Overall negative |

**Worked example (illustrative scores).** Lexicon: good = +2, bad = −2, very = × 1.5, not = flips sign.

| Sentence | Calculation | Result |
| ----- | ----- | ----- |
| "The food was good." | +2 | Positive |
| "The food was very good." | +2 × 1.5 = +3 | Strongly positive |
| "The food was not very good." | +2 × 1.5 = +3, then flipped = −3 | Negative |
| "The food was bad." | −2 | Negative |

**Where rules fail:** sarcasm ("Oh great, another delay"), idioms ("the movie was a killer"), domain shifts ("unpredictable" is good for a thriller, bad for a washing machine), and negation scope in long sentences. Lexicon-and-rule tools such as VADER (Hutto and Gilbert, 2014) are still widely used for short social-media text because they are fast and transparent.

### **6.9 Question Answering**

Symbolic NLP is important in **question answering (QA)** systems that use formal knowledge to interpret a natural-language question and infer the answer.

**How a symbolic QA system works**

| Step | What happens | Medical example: "Which symptoms are associated with pneumonia?" |
| ----- | ----- | ----- |
| 1. Parse the question | Find the question type and its main elements | A "which symptoms" question about the entity *pneumonia* |
| 2. Map words to concepts | Link words to ontology entries | "pneumonia" → `Pneumonia` (a LungDisease), "symptoms" → relation `hasSymptom` |
| 3. Build a formal query | Turn the question into a logical or graph query | `hasSymptom(Pneumonia, ?x)` |
| 4. Reason over the knowledge base | Look up and infer using rules and the ontology | Finds fever, cough, difficulty breathing |
| 5. Generate the answer | Convert the result into a sentence | "Pneumonia is associated with fever, cough and difficulty breathing." |

Inference lets the system answer indirectly: if the ontology says *Pneumonia is-a LungDisease*, and lung diseases are linked to cough, the system can infer cough even when no rule mentions pneumonia directly.

**Strengths:** accurate and explainable when the question falls within the knowledge base, and each answer can show its reasoning.
**Limits:** it only answers what the knowledge base covers, and it needs the question to be understood correctly (paraphrases such as "What does pneumonia feel like?" must also map to the same query).

Early natural-language interfaces to databases and knowledge bases, built in the 1960s and 1970s, worked this way within narrow domains.

---

### **6.10 Information Retrieval**

**Information retrieval (IR)** finds relevant documents in large collections. Symbolic NLP contributes by analyzing and representing the meaning of documents and queries and by using logical inference to match them.

| Technique | How it works | Example |
| ----- | ----- | ----- |
| **Boolean queries** | Combine terms with AND, OR, NOT | `negligence AND "duty of care" NOT criminal` |
| **Thesauri and controlled vocabularies** | Map different words to a preferred term | "car", "automobile", "motorcar" |
| **Query expansion with an ontology** | Add related or more specific concepts to the query | A search for "vehicle" also finds documents about "trucks" |
| **Logical matching** | Represent documents and queries as logical statements and test entailment | A query about "damages for breach of contract" matches statutes encoded with the concept *contract breach* |

**Worked example: legal retrieval.** Legal concepts, statutes and case law are encoded in a structured form. A query is parsed and matched against these representations by inference, returning relevant statutes or judicial opinions, even when different words are used, because the ontology links related legal concepts.

Modern web search relies mostly on statistical and neural ranking, with symbolic structures (knowledge graphs, controlled vocabularies) in a supporting role.

### **6.11 Landmark Symbolic NLP Systems**

| System | Year | What it did | Lesson |
| ----- | ----- | ----- | ----- |
| **ELIZA** (Weizenbaum) | 1966 | Used keyword spotting and **decomposition and reassembly rules** (the DOCTOR script imitated a psychotherapist) | Appearance of understanding without meaning |
| **SHRDLU** (Winograd) | 1972 | Understood and carried out typed commands in a simulated **blocks world** ("Pick up the big red block") | Real understanding was possible, but only in a tiny, fully described world |

Together they show the central trade-off of symbolic NLP: depth within a tightly bounded domain, but poor transfer to open-ended language.

### **6.12 Strengths, Limitations and Challenges**

| Strengths | Limitations |
| ----- | ----- |
| **Transparent:** every decision traces to a rule | **Coverage:** language is open-ended and rules never cover everything |
| **No training data needed** for a first working system | **Ambiguity:** many valid parses and word senses, hard to choose among without world knowledge |
| **Precise** in narrow, well-defined domains (forms, legal or medical terms) | **Brittleness:** unexpected phrasing, misspellings, slang or new words break rules |
| **Controllable:** you can fix a specific error by editing a rule | **Knowledge acquisition bottleneck:** writing grammars, lexicons and ontologies by hand is slow and expensive |
| Combines naturally with logic for **reasoning** | **Maintenance:** large rule sets interact in unexpected ways |
| Good for **safety-critical** or regulated settings where decisions must be justified | **Language change and variation:** rules are tied to one language and one era |

**Challenges to remember**

* **Common-sense knowledge:** understanding "The trophy didn't fit in the suitcase because it was too big" requires knowing that big things don't fit in small ones. Which noun does "it" refer to?
* **Context and pragmatics:** meaning depends on situation and intent, which are hard to write as rules.
* **Scaling:** adding rules for new phrasing eventually produces conflicts and diminishing returns.
* **Evaluation:** a rule that works on examples can fail silently on new text.

#### **Today: hybrid approaches**

Most current systems combine approaches rather than choosing one:

| Hybrid pattern | Example |
| ----- | ----- |
| Rules around statistical models | Neural model proposes entities, hand-written rules validate formats such as dates and IDs |
| Knowledge graphs plus neural language models | A model retrieves facts from a graph to ground its answers |
| Grammars constraining output | A grammar ensures generated text or commands are well formed |
| Ontologies for domain meaning | Medical or legal vocabularies standardize the output of learned extractors |

This is the NLP version of the neuro-symbolic idea introduced in Section 1.

### **6.13 Hands-on (optional)**

**Activity 1: parse a sentence with a grammar (Python and NLTK).**

```python
import nltk

grammar = nltk.CFG.fromstring("""
S   -> NP VP
NP  -> Det N
VP  -> V NP
Det -> 'the'
N   -> 'cat' | 'mouse'
V   -> 'chased'
""")

parser = nltk.ChartParser(grammar)
for tree in parser.parse("the cat chased the mouse".split()):
    print(tree)
# (S (NP (Det the) (N cat)) (VP (V chased) (NP (Det the) (N mouse))))
```

Extension: add `PP -> P NP`, `VP -> V NP PP`, `NP -> NP PP` and the words "saw", "man", "telescope", "with", "I" to the grammar, then parse "I saw the man with the telescope" and count the parse trees. You should get two, one for each reading of the ambiguity.

```prolog
parent(alice, bob).

parent(bob, dave).

% ?- grandparent(alice, W).     W = dave.
% ?- sibling(bob, carol).        true.
```

### **6.14 Summary**

| Topic | Key idea |
| ----- | ----- |
| Symbolic NLP | Processes language with formal rules, logic and symbolic representations |
| Syntax | Grammars (such as CFGs) define valid sentence structures; parsing builds the tree |
| Semantics | Meaning is stored as logical forms, semantic networks, frames or ontologies |
| Rule-based tasks | POS tagging, parsing and information extraction use explicit patterns |
| Logic and inference | Facts and rules let the system derive answers that were never stated |
| Applications | Sentiment analysis, question answering, information retrieval |
| Strength | Transparent, controllable, precise in narrow domains |
| Weakness | Ambiguity, coverage, brittleness and heavy manual effort |
